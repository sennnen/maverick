# M0 — Bedrock

M0 builds the ground everything else stands on: the Rust workspace, the CI gates that police every future change, the documentation system that is the project's system of record, the frozen `mav-model` types that let separate agents work without colliding, a complete and property-tested `mav-frame`, the error and observability machinery that keeps a swarm from shipping silent corruption, and a hello-world UniFFI binding that proves both platforms can link the core. There is no device decoding here and no analytics. The point of M0 is that after it, a work packet can be handed to an agent and the gates will catch it if it does the wrong thing.

M0 is complete when CI is green on the workspace, both platforms link the core, and the docs checks pass.

A note on ownership that applies to every packet below. A packet may edit the `Cargo.toml` of the crate it owns, but only to add dependencies that `architecture.md` permits; it may not edit another crate's `Cargo.toml` and may not edit the workspace root `Cargo.toml`, which P1 owns. `tools/check_deps.py` (built in P3) enforces the allowed edges mechanically. Packets are listed in dependency order; P4 onward can proceed in parallel once P1 through P3 are in.

## Packet M0-P1: Cargo workspace, toolchain, lint policy, CI skeleton

**Owns:** `core/Cargo.toml`, `rust-toolchain.toml`, `rustfmt.toml`, `.gitignore`, `.github/workflows/ci.yml`, and stub crates (a `Cargo.toml` plus an empty compiling `lib.rs`) for `core/crates/mav-model`, `mav-frame`, `mav-obs`, and `mav-ffi`.

**Must not touch:** anything under `docs/`, `tools/`, `connectors/`, `fixtures/`. Do not put real logic in any crate; these are stubs that later packets fill in.

**Contract:** The workspace lists its member crates. The clippy configuration denies `unwrap`, `expect`, `panic!`, `todo!`, and `unimplemented!` in library targets, and allows them in `#[cfg(test)]` and `tests/`. `rust-toolchain.toml` pins one stable toolchain version so every agent and CI build with the same compiler. CI runs, in order and all blocking, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace`. The workflow also has a place to add the two docs checks (added by P2 and P3); leave them wired but pointing at scripts that exist as no-op stubs if necessary, so the pipeline is not red before those packets land.

**Tests first:** This packet is infrastructure, so its "test" is that the empty workspace builds and the gate commands run. Add one trivial passing assertion in `mav-model` (for example, a `const` equality test) so `cargo test --workspace` has something to execute and the harness is proven wired. That assertion is replaced in P4.

**Exit:** `cargo build --workspace`, `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` all pass locally, and the CI workflow runs the same set.

**Notes:** Keep dependency additions out of this packet beyond what a stub needs (nothing). Do not pre-add crypto, `flate2`, or `rustfft`; they are added when a protocol fact demands them, per the dependency rule in PLAN §12. The lint denial of `unwrap`/`expect`/`panic!` is the mechanical form of the "no silent panics" rule from `docs/errors.md`; get it right here and it protects every later packet.

**Status: done.** Decision log: the lint policy is implemented as `[workspace.lints.clippy]` in the root `Cargo.toml` (denying `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented`) inherited by every crate through `[lints] workspace = true`, with `core/clippy.toml` allowing all three in test code. Clippy's in-test allowance only recognises `#[test]` functions, so helper functions in `tests/` integration files carry an explicit crate-level allow with a one-line comment saying why. All twelve stub crates were created, not just the four named here. Verified by construction: an `unwrap` added to library code fails `cargo clippy` and was removed again.

**Owns:** `tools/check_docs.sh`, `CLAUDE.md`, `AGENTS.md`, `README.md`, and stub files for any doc referenced by cross-links that does not yet exist (`docs/architecture.md`, `docs/pipeline.md`, `docs/connectors.md`, `docs/testing.md`, `docs/storage.md`, `docs/ml.md`, `docs/protocol/whoop.md` may be created as short stubs so links resolve). **Contract:** `check_docs.sh` exits non-zero if any of these fail: a relative Markdown link in any `docs/**` or root `*.md` file points at a path that does not exist; `CLAUDE.md` and `AGENTS.md` are not byte-identical; a milestone file exists under `docs/plans/active/` or `completed/` that is not listed in `docs/plans/README.md`. `CLAUDE.md` and `AGENTS.md` follow the ~100-line content spec in PLAN §14: three lines on what mav is, the repo map with one-line descriptions, the build and test commands, the packet-protocol pointer, the skills list, and the short list of universal rules. **Notes:** Keep the script POSIX `sh`, no non-standard dependencies, because it runs in CI and on every agent's machine. The identical-twin rule for CLAUDE.md and AGENTS.md exists because different agent runners read different filenames; the content must never diverge.

**Status: done.** Decision log: the docs landed complete rather than as stubs, so no stub files were needed. The script also checks that every `skills/*/SKILL.md` frontmatter name matches its folder, which the contract did not ask for but doc-gardening wants.

## Packet M0-P3: `check_deps.py`, `architecture.md` dependency edges

**Owns:** `tools/check_deps.py`, `docs/architecture.md`.

**Must not touch:** any crate `Cargo.toml` (this packet reads them, it does not edit them).

**Contract:** `architecture.md` declares the allowed inter-crate dependency edges as a list a machine can parse (for example, a fenced block of `from -> to` lines). The canonical rules: `mav-model` depends on none of our crates and everything may depend on it; a device codec crate may depend on `mav-model`, `mav-frame`, and `mav-codec` only, and specifically may not depend on `mav-store`, `mav-analytic`, `mav-engine`, or any other codec; `mav-ffi` sits at the top and may depend on the crates it exposes. `check_deps.py` parses every `core/crates/*/Cargo.toml`, extracts the intra-workspace dependencies, and exits non-zero if the actual edges are not a subset of the declared allowed edges. It also fails if a crate declared in `architecture.md` is missing from the workspace or vice versa.

**Tests first:** Verify by construction as in P2. Run against the clean tree and confirm it passes. Add a forbidden edge to a scratch copy (for example, make a stub codec depend on `mav-store`) and confirm the script fails and names the offending edge. Note these checks at the top of the script.

**Exit:** `python3 tools/check_deps.py` passes on the clean tree, and CI invokes it.

**Notes:** This is the mechanical enforcement of the boxed-in codec from PLAN principle 3. The codec being unable to reach storage or analytics is not a matter of reviewer vigilance; it is a build failure. Keep the parser tolerant of TOML formatting (use a real TOML parser, not a regex) so it does not break on a reformat.

**Status: done.** Decision log: the script uses a deliberately dumb line parser rather than a TOML library because the system Python on macOS predates `tomllib`; the manifests it reads are workspace-managed and formatted by convention, and the parser is documented as such in the script. The allowed-edges table lives in prose in `architecture.md` and is mirrored as a dict in the script; if the two drift, that is a doc-gardening finding.

## Packet M0-P4: `mav-model` frozen types

**Owns:** all of `core/crates/mav-model/src/`, and may edit `core/crates/mav-model/Cargo.toml` to add `serde`, `serde_json` (dev), and `thiserror`.

**Must not touch:** any other crate.

**Contract:** Define, as the frozen types every other crate consumes:
- Id newtypes: `DeviceId`, `SessionId`, `StreamId`, `FrameId`, `MetadataId`, over `u64` or `uuid` as the type warrants, each with `Copy`/`Eq`/`Hash` where appropriate and `serde` derives.
- Time types: `DeviceTime` (raw device ticks), `WallTime` (UTC nanoseconds), and `ClockMap` as a set of segments mapping device time to wall time. `WallTime` and `DeviceTime` are distinct types and do not silently convert into each other.
- `StreamKind` enum: at least `HeartRate`, `RrInterval`, `Ppg`, `Imu`, `SkinTemp`, `Spo2`, `BatterySoc`, with room to grow. A trailing catch-all is not permitted; an unknown stream is an explicit variant added by an ADR.
- `Sample<T>` with fields `stream: StreamKind`, `device_time: DeviceTime`, `wall_time: Option<WallTime>`, `value: T`, `quality: Quality`, `meta: MetadataId`.
- `Quality { score: f32, reason: Option<RejectReason> }` where `score` is constrained to `0.0..=1.0` at construction and `RejectReason` is an enum of reasons a sample was rejected or downscored.
- `MavError`: a stable numeric `code`, a `category` enum delivered at M0 with `Transport`, `Frame`,
  `Decode`, `Timeline`, `Storage`, `Feature`, `Analytic`, `Ml`, `Ffi`, and `Internal`; ADR-018 later
  appends `Connector`. It also carries a `message`, context chain, and severity. Codes are
  append-only. `MavError` implements `std::error::Error`.
- A `SemVer` type and the convention for `ALGORITHM_VERSION` consts that later crates declare.

Every type is `serde`-serializable. This is the freeze: after M0, any change to `mav-model` requires an ADR under `docs/adr/`. State that rule in a top-of-crate doc comment.

**Tests first:**
- `quality_score_rejects_out_of_range` — constructing a `Quality` with a score below 0 or above 1 fails or clamps per the chosen contract; assert the exact behaviour.
- `sample_serde_round_trips` — a fully populated `Sample<u16>` serialises to JSON and deserialises back to an equal value.
- `deviceid_and_sessionid_are_distinct_types` — a compile-fail or type-level test that a `DeviceId` cannot be passed where a `SessionId` is expected.
- `clockmap_segment_ordering` — segments are queryable by device time and return the correct wall-time mapping for a value inside a segment and `None` outside all segments.
- `maverror_category_is_stable` — assert the numeric discriminants or code ranges of each category so an accidental reorder is caught.

**Exit:** `cargo test -p mav-model`, `cargo clippy -p mav-model --all-targets -- -D warnings`, `cargo fmt --check`.

**Notes:** This packet is the reason the swarm can work in parallel, so it is worth over-specifying. Prefer explicit types over generics where a stream's value type is known. Do not add `ClockMap` interpolation of any kind; a `ClockMap` maps, it does not invent intermediate values (PLAN pipeline section). The `MavError` category set is closed and matches `docs/errors.md`; if you need a category that is not listed, that is an ADR, not a new variant slipped in here.

**Status: done.** Decision log, deltas from the contract as written: the sample's fields are named `kind` (not `stream`) and `provenance` (not `meta`), and a `seq: u16` per-second occurrence index was added so the RR dedup tiebreaker exists from the start. `StreamKind` carries `Spo2Raw` and `RespRaw` rather than `Spo2`, because the ledger says these are stored as raw ADC on device and naming them raw keeps anyone from treating them as percentages. A `raw` module (`RawValue`, `RawSample`, `RawSampleBatch`) was added as the Decode-to-SQI boundary type, and the error codes gained a `codes::ALL` registry so tests can hold the constants, the docs catalogue, and the list in step. The `SemVer` type is named `Version`.

## Packet M0-P5: `mav-frame` CRC-8, CRC-16/Modbus, CRC-32

**Owns:** `core/crates/mav-frame/src/crc.rs` (new) and its test module. May edit `core/crates/mav-frame/Cargo.toml` to add `proptest` as a dev dependency.

**Must not touch:** the reassembler and TypedReader files (owned by P6). Do not add the `crc` crate as a dependency; these are hand-rolled and fixture-tested, which keeps the crate zero-dependency and lets the property tests prove correctness.

**Contract:** Implement three checksums with exactly these parameters, taken from `docs/protocol/whoop.md`:
- CRC-8: polynomial `0x07`, init `0x00`.
- CRC-16/Modbus: polynomial `0xA001` (reflected), init `0xFFFF`.
- CRC-32: zlib, reflected, polynomial `0xEDB88320`.
Each is a pure function from a byte slice to its checksum. No allocation, no panics on empty input.

**Tests first:**
- `crc8_known_answers`, `crc16_modbus_known_answers`, `crc32_zlib_known_answers` — each asserts the checksum of a fixed input against a value computed independently (a published test vector or a second implementation), not against the function's own output.
- `crc32_matches_gen5_hello` — the CRC fields inside the known gen5 hello frame `aa0108000001e67123019101363e5c8d` validate: the CRC-16/Modbus over bytes `[0..=5]` equals the two header CRC bytes, and the trailing CRC-32 over the padded payload validates. This ties the checksums to a real captured frame.
- `crc_empty_input` — each function returns its defined value for an empty slice without panicking.
- `crc_is_deterministic` (proptest) — for any byte vector, computing the checksum twice yields the same value.

**Exit:** `cargo test -p mav-frame`, `cargo clippy -p mav-frame --all-targets -- -D warnings`, `cargo fmt --check`.

**Notes:** The frame docs in both surveyed codebases were wrong in prose but the code was right, which is why the contract here cites the code-derived constants and the real hello frame rather than any prose description. If a known-answer test disagrees with your implementation, the implementation is wrong; do not adjust the expected value to match your output.

**Status: done.** Decision log: CRC-32 is table-driven (const-built 256-entry table) because it covers whole payloads and historical syncs push megabytes through it; the two header CRCs stay bitwise. Known-answer vectors are the standard `123456789` check values plus the captured gen5 hello, which the gen5 builder reproduces byte for byte.

## Packet M0-P6: `mav-frame` reassembler and TypedReader

**Owns:** `core/crates/mav-frame/src/reassembler.rs` (new), `core/crates/mav-frame/src/reader.rs` (new), their test modules, and `fixtures/frame/gen5_hello_v1.json` plus `fixtures/frame/gen4_frame_v1.json`.

**Must not touch:** `crc.rs` (P5 owns it; consume it as a dependency within the crate).

**Contract:** The reassembler consumes a stream of bytes and emits complete, CRC-valid frames. It buffers incoming bytes, discards everything before an `0xAA` start-of-frame byte, peeks the declared length to compute the expected total, and emits a frame once the buffer holds at least that many bytes. It resynchronises on garbage by dropping to the next `0xAA`. A maximum frame size of 8192 bytes bounds a runaway declared length; a declared length above the cap is a logged rejection, not a hang. The two frame layouts, from `docs/protocol/whoop.md`:

- gen4, 4-byte header: `[0]=0xAA`, `[1..=2]=declared_len` u16 LE (equal to payload length plus 4, and it includes the trailing CRC-32), `[3]=CRC8(bytes[1..=2])`, `[4..]=payload` (not padded), trailing `CRC32(payload)` u32 LE. Total length is `declared_len + 4`.
- gen5, 8-byte header: `[0]=0xAA`, `[1]=0x01` (format/version), `[2..=3]=declared_len` u16 LE (equal to the padded payload length plus 4), `[4..=5]=0x00 0x01` (reserved), `[6..=7]=CRC16/Modbus(bytes[0..=5])` LE, `[8..]=payload` zero-padded to a 4-byte boundary, trailing `CRC32(padded payload)` u32 LE. Total length is `declared_len + 8`.

A frame whose header CRC or trailing CRC fails validation is rejected with a `Frame`-category `MavError` code and a reason; it is never emitted and never silently dropped. Truncated data is tolerated only for realtime and historical data packet types, never for commands.

`TypedReader` wraps a validated frame payload and offers bounds-checked little-endian reads (`u8`, `u16`, `u32`, `i16`, `f32`, and byte slices) that return a `Frame`-category error on an out-of-bounds read rather than panicking.

**Tests first:**
- `reassembles_gen5_hello` — feeding the bytes of `aa0108000001e67123019101363e5c8d` yields exactly one frame with the expected payload, matching `fixtures/frame/gen5_hello_v1.json`.
- `reassembles_gen4_frame` — a constructed valid gen4 frame round-trips, matching its fixture.
- `drops_leading_garbage_then_syncs` — random leading bytes before the `0xAA` are discarded and the following valid frame still emits.
- `rejects_bad_header_crc` and `rejects_bad_trailing_crc` — a frame with a corrupted CRC is rejected with the expected error code and produces no emitted frame.
- `bounds_the_max_frame_size` — a declared length above 8192 is rejected, and the reassembler does not buffer unboundedly.
- `split_across_reads_reassembles` (proptest) — for any frame split into arbitrary byte chunks fed in sequence, the same single frame is emitted.
- `typedreader_out_of_bounds_errors` — reading past the payload end returns an error, never panics.

**Exit:** `cargo test -p mav-frame`, `cargo clippy -p mav-frame --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh` (the new fixtures are referenced correctly).

**Notes:** The reassembler and TypedReader are on the property-test-mandatory list in `docs/testing.md`, so the split-across-reads and out-of-bounds properties are not optional. The two fixtures are generated, not hand-edited; follow `skills/golden-fixtures`. Do not special-case decode logic here — this crate turns bytes into validated frames and nothing more; interpreting the payload is Decode's job in M1.

**Status: done.** Decision log: the fixtures live at `fixtures/frame/gen5_hello_v1.json` (transcribed from the real capture both surveyed codebases carry, tagged XVAL) and `fixtures/frame/gen4_frame_v1.json` (synthetic, generated with an independent Python implementation rather than the code under test, tagged PROV until a real gen4 capture replaces it). Truncation tolerance for data packet types is deferred to the decode work in M1, where packet types first become known; the reassembler currently rejects any frame that fails CRC regardless of type, which is the conservative reading.

## Packet M0-P7: `mav-obs` tracing, Tap trait, ring log, and `docs/errors.md`

**Owns:** all of `core/crates/mav-obs/src/`, `docs/errors.md`. May edit `core/crates/mav-obs/Cargo.toml` to add `tracing` and `tracing-subscriber`.

**Must not touch:** `mav-model` (consume `MavError` from it; do not redefine error types here).

**Contract:** Provide the observability surface described in PLAN §7 and the error policy in `docs/errors.md`:
- A `Tap` trait with `fn on_stage(&self, stage: Stage, event: TapEvent)`, where `Stage` names each pipeline boundary and `TapEvent` carries counts, relevant ids, and, in debug builds only, a payload summary. Ship two default taps: a counters tap and a ring-log tap.
- An in-memory ring buffer log with a fixed capacity that is always on and cheap, holding recent structured events including every rejection with its `MavError` code and reason. Expose a query that returns the recent slice.
- A `tracing` initialiser that sets up one span per stage per unit of work, with frame, session, and stream ids attached as span fields.
- `docs/errors.md` documents the category set (matching `mav-model`'s `MavError`), the numbering convention (codes are append-only and never reused), the severity levels, and the rule that no packet, sample, or frame is ever discarded without logging a code and a reason.

The SQLite error journal and the `export_report_bundle()` zip are not in M0 because they need `mav-store` (M1); `docs/errors.md` describes them as the next step and the ring buffer stands in until then.

**Tests first:**
- `ring_log_retains_recent_and_evicts_oldest` — pushing more events than the capacity keeps the most recent and drops the oldest, and the count is exactly the capacity.
- `tap_receives_stage_events` — a test tap records the stages and events it is handed in order, asserting the exact sequence.
- `rejection_is_logged_with_code_and_reason` — a simulated rejection lands in the ring log with the expected `MavError` code and a non-empty reason.
- `errors_md_codes_are_unique` — a small test or a `check_docs` extension parses `docs/errors.md` and asserts no code appears twice.

**Exit:** `cargo test -p mav-obs`, `cargo clippy -p mav-obs --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** Debug-only payload summaries must compile out of release builds so there is no cost and no chance of leaking raw health bytes into a log in production. The counters tap and ring-log tap are the default observability from day one; later pipeline stages call the `Tap` at their boundaries rather than logging ad hoc.

**Status: done.** Decision log, one delta: `tracing-subscriber` was not added. The core only creates spans (`stage_span`) and installing a subscriber is the host's job, since the apps and `mav-replay` will each want their own sink and format; a subscriber dependency in the core would be speculative. The ring-log test asserts eviction through the monotonic `seq` field so gaps after eviction are visible, and `docs/errors.md` gained the code catalogue table, held in step with `codes::ALL` by `mav-obs/tests/errors_doc_sync.rs`.

## Packet M0-P8: `mav-ffi` UniFFI hello-world binding, both platforms

**Owns:** all of `core/crates/mav-ffi/src/`, the UniFFI definition (proc-macro attributes or a `.udl`), `apps/ios/README.md`, `apps/android/README.md`. May edit `core/crates/mav-ffi/Cargo.toml` to add `uniffi`.

**Tests first:**
- `ffi_version_matches_crate_version` — the version the FFI function returns equals the crate's own version constant.
- `ffi_record_round_trips` — the struct returned across the boundary carries the expected field values.

**Notes:** This is the packet that satisfies the M0 exit clause "both platforms link the core", so it is deliberately tiny in surface and complete in plumbing. Both Swift and Kotlin bindings generate from the built library and expose `coreVersion()` and `runCapture(...)`, and CI runs that generation on every push. Fixture tests prove the FFI reproduces the frozen session hash `33143ef069a85a38` and PRV analytics hash `e77c7b04c7fceb2c`, so the surface returns exactly what `mav-replay` does. The exact `.xcframework` / `jniLibs` packaging and the simulator link need Xcode and the Android NDK and are documented in the platform READMEs as local steps for the app milestone; everything short of the device link is verified here.

## M0 exit

M0 is done when, on a clean checkout: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` pass; `tools/check_docs.sh` and `tools/check_deps.py` pass; UniFFI bindgen produces Swift and Kotlin sources; and both platform READMEs' documented builds produce a linkable artifact against the core. When that is true, this file moves to `docs/plans/completed/M0.md` with a short retro: what surprised us, what drifted from this plan, and which doc fixes were filed.

## Retro

M0's exit condition holds on a clean checkout and has held continuously since: the workspace builds,
the three Rust gates and both documentation gates pass, and UniFFI generates Swift and Kotlin from
one definition. The file sat in `active/` long after that was true, which is the drift this retro
records.

**What surprised us.** The observability packet landed before anything produced data to observe, and
that turned out to be the wrong order in one specific way: `mav-obs` was complete, correct, tested —
and reachable from nothing for the whole of M1 and the WC lane. The Tap trait was not wired to the
live path until LP-P6, roughly a year of packets later. Building the observer first is right;
leaving it unwired is how "errors and observability are milestone zero" became a sentence rather
than a property.

**What drifted from the plan as written.** `tracing-subscriber` was deliberately not added (recorded
in M0-P7). `mav-frame` and `mav-codec` were completed here and then stranded: ADR-016 and ADR-017
moved device knowledge into signed Wasm artifacts, which cannot reach a host crate, so both became
islands. Their disposition is decided in the gardening lane, not here.

**Doc fixes filed as a result.** The repository layout in `docs/PLAN.md` had never been updated for
the five `mav-connector-*` crates M0 did not anticipate; G-P1 added them.

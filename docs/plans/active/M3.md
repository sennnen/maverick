# M3 — RR variability and honest availability

M3 adds real beat-to-beat variability and proves capability negotiation without inventing a
Recovery score. The original milestone said Recovery should compute and proposed proving its
absence with a fake device. That was the wrong bar twice: no public or fixture-validated Recovery
formula exists, and a missing stream can be tested directly as a capability set without pretending
there is another physical device.

M3 exits when a real or source-derived RR capture produces time-domain variability through the
shared pipeline, PPG-derived intervals are labelled pulse-rate variability rather than ECG HRV, and
the availability snapshot reports exact reasons for both missing inputs and unadmitted algorithms.

---

## Packet M3-P1: Time-domain interval variability and capability negotiation

**Owns:** `core/crates/mav-analytic/`, `docs/analytics.md`, this status entry.

**Must not touch:** device connectors, recovery scoring, sleep, strain, or platform UI.

**Contract:** Implement mean interval, RMSSD, sample SDNN, NN50, and pNN50 from the 1996 ESC/NASPE
definitions. Inputs are scored `RrInterval` samples; sort by `(device_time, seq)`, exclude and count
poor-quality or physiologically implausible intervals, and never correct or interpolate. Require an
`IntervalSource`, labelling PPG output as pulse-rate variability. Add a data-driven analytic
availability table: time-domain variability requires RR and is admitted; Recovery requires RR but
is `algorithm_not_admitted`.

**Tests first:**

- a hand-calculated vector asserts every metric;
- equal RR values at the same second but different `seq` remain two intervals;
- shuffled input produces the same output;
- bad-quality and out-of-range inputs are excluded and counted;
- fewer than three accepted intervals is unavailable;
- PPG output cannot call itself ECG HRV;
- missing RR reports the exact stream;
- RR makes variability available but does not make Recovery available.

**Exit:** `cargo test -p mav-analytic`, workspace clippy/fmt, docs and dependency checks.

**Status: done.** Ten tests. The implementation deliberately does not approximate the
Lipponen–Tarvainen classifier: it applies the upstream quality gate and 300–2000 ms plausibility
range, then leaves every excluded interval visible in the count. Recovery remains an explicit
unavailable node rather than a speculative score.

## Packet M3-P2: RR capture through the pipeline

**Owns:** RR fixture files under `fixtures/replay/`, RR plumbing in `mav-engine`, the replay snapshot
extension, and their tests.

**Must not touch:** connector protocol claims without a source, Recovery scoring, or platform UI.

**Contract:** Extend the existing replay slice so a capture containing RR intervals reaches SQI,
timeline, storage, `mav-analytic::time_domain`, and a deterministic snapshot. The fixture must come
from a real/source capture or be independently generated from a documented packet layout and marked
provisional. Snapshot provenance names interval source and algorithm version.

**Tests first:** exact decoded RR sequence including equal same-second values; frozen RMSSD/SDNN/
pNN50 output; stable canonical hash; corrupt or rejected RR counted rather than silently removed.

**Exit:** replay reproduces the frozen variability snapshot and all workspace gates pass.

**Status: done.** Manifests declare `interval_source`, the
pipeline reads stored RR samples into `mav-analytic`, writes provenance, and produces a fixed-point
`analytics-snapshot/v1` beside the unchanged M1 snapshot. An inline gen5 packet-layout test covers
equal same-second intervals, a zero placeholder, a rejected 50 ms interval, the exact
RMSSD/SDNN/pNN50 values, PPG labelling, and Recovery's unadmitted state.
`fixtures/replay/realtime_rr_prv_v1` now freezes the same path from raw gen5 bytes through replay:
packet offsets come from the `[XVAL]` realtime layout, frame CRCs were generated independently, and
the analytics hash is `e77c7b04c7fceb2c`. `mav-replay` prints both the unchanged M1 snapshot and
the analytics snapshot with their separate hashes.

## Packet M3-P3: Availability over FFI

**Owns:** availability snapshot assembly in `mav-engine`, the UniFFI record surface in `mav-ffi`,
and binding-generation tests.

**Must not touch:** Recovery formula or connector-specific UI logic.

**Contract:** Expose analytic availability beside values. The platform receives analytic id,
available boolean, and a structured unavailable reason. No UI code asks whether a device is WHOOP,
gen4, gen5, or MG.

**Tests first:** no RR gives `missing_streams`; RR gives variability available; RR still gives
Recovery `algorithm_not_admitted`; Swift and Kotlin bindings generate the structured records.

**Exit:** Rust tests and both bindgen targets pass in CI.

**Status: pending.**

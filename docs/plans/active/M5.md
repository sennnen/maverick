# M5 — Historical sync and canonical merge

M5 makes stored history a first-class input to the same pipeline as realtime data. It starts before
M4 because the protocol sequence is documented and testable now, while sleep staging still lacks a
labelled night capture. Milestone numbers describe product areas, not a required calendar order.

The central invariant is stronger than “sync completes”: Maverick never advances a device cursor
past bytes that were not durably stored. A historical acknowledgement is emitted only after the
corresponding burst has committed. `FORCE_TRIM` is a separate destructive command and is not part of
the automatic controller.

M5 exits when a captured or corpus-pinned historical transfer can be replayed twice into one
canonical series, with the second pass producing duplicates rather than extra rows; every emitted
acknowledgement is proven to follow durable persistence; admitted record versions decode through
version-specific layouts; unknown versions remain raw evidence with a typed error; and the affected
day set is deterministic.

## Packet M5-P1: Safe historical transfer controller

**Owns:** `core/crates/mav-engine/src/historical.rs`, its tests, the module export, and this status
entry.

**Must not touch:** record decoding, SQLite schema, platform BLE, connector manifests, analytics,
or `FORCE_TRIM`.

**Contract:** Add a pure controller driven by injected events. It owns no radio, database, or
clock. Configuration supplies command templates for `GET_DATA_RANGE`, `SEND_HISTORICAL_DATA`, and
`HISTORICAL_DATA_RESULT`; command opcodes, `b3`, and initial payloads remain connector data.

The controller states are:

- `Idle`
- `AwaitingRange`
- `AwaitingSendAcceptance`
- `Receiving`
- `AwaitingDurableCommit`
- `Complete`
- `Failed`

The controller accepts:

- `Start`
- `Response { to_opcode, origin_seq, result }`
- `BurstStarted`
- `BurstEnded { ack_payload, record_count }`
- `BurstPersisted`
- `PersistFailed { reason }`
- `HistoryComplete`
- `Timeout`
- `Disconnect`

It emits ordinary acquisition `Command` values. `Start` emits `GET_DATA_RANGE`. Its matching
successful response emits `SEND_HISTORICAL_DATA`. A send result of `pending` leaves the controller
waiting; `ok` enters `Receiving`. `BurstEnded` stores the opaque acknowledgement payload but emits
nothing. Only `BurstPersisted` emits `HISTORICAL_DATA_RESULT`, byte-for-byte with that payload.
`PersistFailed`, timeout exhaustion, or disconnect emits no acknowledgement and enters `Failed`.
`HistoryComplete` is accepted only from `Receiving`, with no burst awaiting persistence.

The controller never interprets an acknowledgement cursor and never constructs `FORCE_TRIM`.
Opaque cursor bytes are safer than a guessed cross-generation structure.

**Tests first:**

- `start_requests_the_data_range`
- `range_success_requests_history`
- `pending_send_response_does_not_restart_or_ack`
- `burst_end_never_acks_before_persistence`
- `persisted_burst_acks_exact_payload_once`
- `persist_failure_permanently_blocks_the_ack`
- `history_complete_is_rejected_while_a_burst_is_uncommitted`
- `wrong_sequence_does_not_advance_the_controller`
- `timeouts_retry_to_the_exact_budget_then_fail_closed`
- `disconnect_with_uncommitted_data_emits_no_command`
- `controller_has_no_force_trim_action`

**Exit:** `cargo test -p mav-engine historical`, strict clippy, formatting, docs and dependency
checks.

**Status: done.** Eleven state-machine tests prove command order, exact sequence matching, pending
responses, bounded retries, durable-persist-before-ack, failure and disconnect behaviour, completion
gating, and the absence of any force-trim action. The controller stays separate from realtime
acquisition, logs every transition, treats cursor bytes as opaque, and emits only the three command
templates the caller supplies. Error codes 1004 and 1005 distinguish unsafe historical ordering
from a device command rejection. All workspace gates pass.

## Packet M5-P2: Typed historical control decode

**Owns:** historical control types in `mav-model`, control-packet parsing in `mav-codec`, fixture
files for metadata and command responses, and tests.

**Must not touch:** versioned biometric record layouts, storage, platform BLE, or analytics.

**Contract:** Decode only the control facts needed by P1:

- command-response opcode, origin sequence, and result (`pending`, `ok`, or exact unknown byte);
- metadata `START`, `END`, and `COMPLETE`;
- the complete opaque acknowledgement payload carried by `END`;
- record count when the wire provides one.

Parsing is generation-specific where offsets differ and fixture-pinned in both directions. Unknown
metadata kinds remain typed unknown values and are logged once; malformed lengths return
`DECODE_FIELD_UNREADABLE`. No parser guesses an eight-byte cursor by scanning arbitrary offsets.

**Tests first:**

- one gen4 command-response fixture;
- one gen5 command-response fixture;
- `START`, `END`, and `COMPLETE` fixtures;
- `END` preserves every acknowledgement byte;
- truncated metadata fails with a stable error;
- unknown metadata is not mistaken for completion.

**Exit:** every control fixture round-trips or decodes to an exact expected JSON value; workspace
gates pass.

**Status: done.** `mav-model::historical` carries the typed facts (`ControlResult`,
`HistoricalControl`) and `mav-codec::control::decode_control` parses them from validated payloads.
Five [PROV] fixtures under `fixtures/control/` were built with an independent Python implementation
of both envelopes and decode to exact JSON; truncation returns `DECODE_FIELD_UNREADABLE`, unknown
metadata stays typed unknown, and data packets return `None`. Decision log: the inner header is
[XVAL] generation-independent, so one parser serves both generations — the gen4/gen5 split lives in
the envelope the reassembler already owns, and the gen5 hello frame (command data at `[3]`) is the
evidence control bodies do not shift the way realtime layouts do. `END` keeps every byte after the
kind as the opaque ack payload, including the gen5 pad byte, because nothing may parse or trim a
cursor. `record_count` decodes to `None`: no admitted source pins one inside `END`, and inventing an
offset is exactly what the packet forbids; the slot exists for the capture that proves it.

## Packet M5-P3: Durable burst boundary

**Owns:** burst orchestration in `mav-engine`, transaction support in `mav-store`, and tests.

**Must not touch:** record-version layouts, connector manifests, analytics formulas, or platform UI.

**Contract:** Collect decoded samples for one `START…END` burst, run SQI and timeline placement, and
commit the burst in one SQLite transaction. Return a durable receipt only after commit succeeds.
Feed `BurstPersisted` to P1 only from that receipt. A decode, SQI, timeline, or storage failure aborts
the transaction and feeds `PersistFailed`; no cursor acknowledgement can escape.

Raw frame evidence is stored before or in the same transaction as decoded samples once the raw-frame
table exists. Until then, the fixture capture remains the replayable tier-one source and this
limitation is stated in the packet status.

**Tests first:**

- a two-record burst commits atomically;
- an injected failure on record two leaves zero rows from the burst;
- the controller emits no ack after rollback;
- replaying the committed burst reports duplicates and leaves counts unchanged;
- two equal RR intervals with different `seq` both survive.

**Exit:** a failure-injection test proves the safe-ack invariant across controller and SQLite.

**Status: done.** `mav-store` gains `in_transaction` (BEGIN IMMEDIATE; commit on Ok, rollback on
Err, with a rollback failure appended to the original error's context) and
`mav-engine::burst::HistoricalBurst` collects decoded samples, runs SQI and timeline placement, and
commits the burst in one transaction, returning a `BurstReceipt` only after commit succeeds. Tests
prove the two-record atomic commit, that replaying a committed burst reports duplicates and changes
nothing, that two equal RR intervals with different `seq` both survive, and the cross-layer
safe-ack proof: an injected failure on record two leaves zero rows and the resulting
`PersistFailed` drives the controller to `Failed` with no acknowledgement command. Limitation per
the contract: the raw-frame evidence table does not exist yet, so the fixture capture remains the
replayable tier-one source; feeding real `HISTORICAL_DATA` decode into bursts arrives with P4–P7.

## Packet M5-P4: Admit versioned record decoders

**Owns:** `record_versions` schema resolution, one decoder module per admitted record version,
version fixtures, and protocol-ledger status updates.

**Must not touch:** unverified v20 optical fields, unverified v21 IMU calibration, MG ECG,
Recovery, sleep staging, or fallback decoding of unknown versions.

**Contract:** A record version lands only with a real capture, a corpus-pinned byte vector from a
named source, or an independently checkable published layout. Each version has an exact minimum
length, field offsets, signedness, scale, output stream kinds, confidence tags, and golden expected
JSON. Unknown versions produce no samples; their raw bytes remain available and the error journal
records the version. There is no “try V24 and plausibility-gate the result” fallback.

Admission order:

1. gen5/MG R20 K=18 per-second metrics, limited to corpus-pinned fields;
2. gen5/MG R20 K=26 raw optical samples, preserving raw ADC units;
3. gen4 V24 solid fields only;
4. other versions only when their own evidence arrives.

Fields marked residual, refuted, unknown, or unverified in `docs/protocol/whoop.md` stay absent from
the model. In particular v20 remains wholly undecoded, v21 remains unadmitted, and K=18 bytes 33/40
cannot become cardiac alerts.

**Tests first per version:**

- exact byte length boundaries;
- exact timestamp and every admitted field;
- signed and fixed-point conversions;
- zero/invalid sentinels;
- truncation and unknown-version errors;
- stable expected JSON;
- no output stream exists for unadmitted fields.

**Exit:** every emitted sample traces to a fixture byte range and ledger claim.

**Status: done for the MG slice; gen4 V24 deferred on its own admission rule.** The manifest's
`record_versions` map now names admitted decoder ids (`r20_k18`, `r20_k26`) — validated against
`records::ADMITTED_DECODERS` at parse time, because these layouts carry bit fields and sentinel
semantics the manifest DSL cannot express — and `ManifestCodec` routes layout-less
`historical_data` packets through them. K=18 emits exactly HR (`body[11]`, zero = no-lock
sentinel, no sample), skin temp (`body[62:64]` i16 LE centidegrees), and the packed sleep state
(bits 5–4 of `body[70]`) as the new additive `SleepStateRaw` stream; the tri-mode SpO2 byte,
secondary HR, and every residual/refuted byte are proven ignored by fixture noise. K=26 emits 24
raw-ADC i16 photodiode samples keyed `(second, seq)` with no invented sub-second phase. Unknown
versions return the new `DECODE_UNKNOWN_RECORD_VERSION` (3005) and produce nothing. Decision log:
V24 did not land because the ledger itself says its offsets must be pinned from a fixture, not
prose, and no V24 byte vector exists in this repository — admitting it now would violate this
packet's first sentence; it waits for a capture or a named-source vector. Fixtures are [PROV]
synthetic to the corpus-pinned offsets, built with an independent Python implementation.

## Packet M5-P5: Canonical realtime/history merge

**Owns:** historical replay path in `mav-replay`, merge orchestration in `mav-engine`, timeline
tests, and expected snapshots.

**Must not touch:** connector transport, record fields not admitted by P4, or analytics formulas.

**Contract:** Feed historical and realtime samples through the same SQI, timeline, and store path.
Ordering is independent of arrival order. Exact duplicates collapse; equal RR values with distinct
sequence numbers remain. Device timestamps remain immutable. Implausible times use an explicit
clock mapping or capture fallback and carry the rejection reason.

**Tests first:**

- history before realtime and realtime before history produce identical rows;
- replay twice is idempotent;
- overlap at the sync boundary stores one copy;
- a stale device clock does not mutate raw time;
- stable snapshot hashes survive input permutation.

**Exit:** one mixed capture replayed in at least three arrival orders yields identical canonical
JSON and hashes.

**Status: done.** The merge needed no new orchestration: M5-P4's packet-47 routing means
`run_realtime` already drives history and realtime through the one decode→SQI→timeline→store
path, and `mav-replay` replays a mixed capture unchanged. `fixtures/replay/mixed_history_v1`
mixes realtime seconds with K=18 records, a duplicated historical chunk, and a stale-clock
record. Tests prove: three arrival orders (original, reversed, rotated) produce identical stored
rows for every stream and identical snapshot hashes; replaying twice into one store is
idempotent; the duplicated chunk stores once; and the stale record keeps its raw device time
while its wall time falls back to the capture wall with the implausible-timestamp reason. The
frozen expected snapshot (current 62 bpm, mean 60.5 over four seconds) is checked by hand in the
fixture's evidence note.

## Packet M5-P6: Affected-day recompute trigger

**Owns:** trigger and affected-window types in `mav-engine`, deterministic day-set tests, analytics
cache invalidation hooks, and documentation.

**Must not touch:** platform schedulers, notification UI, or new analytics.

**Contract:** A completed sync returns the set of local calendar days touched by newly inserted
samples. Duplicates do not dirty a day. The set is sorted and unique. The engine invalidates only
cached computations whose input window intersects those days, then recomputes admitted analytics.
Timezone is injected; no core code reads the system timezone or clock.

**Tests first:**

- one burst spanning midnight dirties two days;
- duplicate-only replay dirties none;
- mixed inserted/duplicate data dirties only inserted days;
- timezone changes the day boundary deterministically;
- interrupted sync emits no completion trigger.

**Exit:** a historical replay reports exact affected days and a second replay reports none.

**Status: pending.**

## Packet M5-P7: FFI progress and failure report

**Owns:** historical status snapshot in `mav-engine`, UniFFI facade fields/functions, generated
binding checks, and platform README updates.

**Must not touch:** native BLE implementation or UI layout.

**Contract:** Hosts receive state, records seen, records inserted, duplicates, rejected records,
last durable cursor hash, affected days, and a stable failure code. Raw cursor bytes do not cross
FFI or enter logs. Progress is a read model; platform code cannot command trim or synthesize an ack.

**Tests first:** canonical status JSON/hash; cursor redaction; structured persistence failure;
Swift/Kotlin bindgen fields.

**Exit:** both host languages can render honest progress and error state without reproducing the
controller.

**Status: pending.**

# M1 — First vertical slice: realtime heart rate

M1 takes one signal all the way through the pipeline: a realtime heart rate reading from a WHOOP 5.0 capture, from raw bytes to a snapshot the UI could render, and it does it identically on both platforms. Nothing here is broad. It is one stream, one device family, one metric, chosen because a thin slice that runs end to end proves the architecture in a way that a wide layer never does. When M1 is done, the shape of every later stream is already set, because every later stream walks the same path this one cut.

The exit criterion is exact and mechanical: the same capture file, run through the shared core, produces a byte-identical snapshot hash on the iOS and Android simulators. Any divergence is a bug in the thin bindings by definition, because the core is one piece of Rust that both platforms link.

Everything on the protocol side comes from `docs/protocol/whoop.md` and carries a confidence tag. The realtime layout used here is tagged `[XVAL]` (both surveyed codebases agree, and the heart rate was cross-checked against the standard GATT characteristic to within half a beat per minute), which is about as much confidence as we have without a strap. It is still not hardware-verified, and the whoop5 manifest and the capture fixture both say so.

Packets are listed in dependency order. P1 through P3 lay the connector and transport foundations; P4 through P8 are the pipeline stages; P9 through P11 assemble the snapshot, drive the whole thing from a fixture, and prove parity. The ownership rule from M0 still holds: a packet edits only the files it owns and only its own crate's `Cargo.toml`, and `tools/check_deps.py` enforces the dependency edges.

## Packet M1-P1: Acquisition state machine and command layer

**Owns:** `core/crates/mav-engine/src/acquisition.rs` (new) and its test module. May edit `core/crates/mav-engine/Cargo.toml` to depend on `mav-model`, `mav-frame`, and `mav-obs`.

**Must not touch:** any codec, manifest, or decode file. This packet moves bytes and manages connection state; it does not interpret payloads.

**Contract:** A pure-Rust state machine driven entirely by injected events, with no radio dependency, so the whole of it is unit-testable. States, exactly: `Disconnected`, `Scanning`, `Connecting`, `Authenticating`, `Configuring`, `Streaming`, `HistoricalSync`, `Idle`. Every transition emits a `Tap` event and is logged. The command layer matches requests to responses by sequence number, times out after a bounded interval, and retries at most three times with exponential backoff before surfacing a `Transport`-category `MavError`.

For the gen5 WHOOP the handshake and start sequence, from the ledger, is: on connect, write the fixed 16-byte hello, which is `GET_HELLO` (command 145) with sequence 1 and data `[0x01]`, moving `Authenticating` toward `Configuring`; then write `toggle_realtime_hr` (command 3) to move `Configuring` to `Streaming`. Frames are CRC-checked, never encrypted; there is no cryptographic handshake. Real access control is OS-level BLE bonding, which is the native transport's concern and not modelled here. Incoming bytes in `Streaming` are handed to `mav-frame`'s reassembler; emitted frames are passed on to the decode stage (wired in P4).

**Tests first:**
- `handshake_reaches_streaming` — feeding the injected connect event, then a hello response, then a realtime-toggle acknowledgement, walks the machine `Disconnected -> Scanning -> Connecting -> Authenticating -> Configuring -> Streaming` and asserts the exact state after each event.
- `command_retries_then_fails` — a command whose response never arrives retries exactly three times with increasing backoff and then yields a `Transport` error with the expected code.
- `sequence_mismatch_is_rejected` — a response carrying the wrong sequence number is not matched to the outstanding request and is logged as a rejection.
- `disconnect_transitions_to_disconnected_from_any_state` — an injected disconnect event from `Streaming`, `Configuring`, and `HistoricalSync` each lands in `Disconnected` and logs the transition.

**Exit:** `cargo test -p mav-engine`, `cargo clippy -p mav-engine --all-targets -- -D warnings`, `cargo fmt --check`.

**Notes:** The reason the machine takes injected events rather than owning a transport is that the surveyed codebases could never CI-test their BLE state machines, because those machines were welded to CoreBluetooth. Ours is pure and event-driven, so `mav-replay` and unit tests exercise it fully; only the thin native shim that feeds it real bytes stays untested until hardware. The macOS CoreBluetooth limitation (it cannot complete the gen5 bond, so config writes are iOS and Android only) is a transport-shim concern to record in `docs/connectors.md`, not a state in this machine.

## Packet M1-P2: `mav-codec` — DeviceCodec trait, manifest types, registry

**Owns:** all of `core/crates/mav-codec/src/`, `docs/connectors.md`. May edit `core/crates/mav-codec/Cargo.toml` to depend on `mav-model`, `mav-frame`, `serde`, and `serde_json`.

**Must not touch:** `mav-store`, `mav-analytic`, `mav-engine`. The codec crate sits low in the graph and `check_deps.py` will fail if it reaches upward.

**Contract:** Define the connector abstraction from PLAN principle 3.
- Manifest types that deserialise from a `manifest.json`: device identity, GATT UUIDs, frame parameters (start-of-frame byte, header layout, which CRCs apply), the packet-type map, per-record field layouts (offset, width, endianness, type, and unit conversion for each field), record versions, and the declared capability set (which `StreamKind`s this device can produce).
- The `DeviceCodec` trait: it receives bytes, its own manifest, and a per-device key-value store handle, and returns frames and samples. Its interface gives it no way to reach storage, network, analytics, or another device. A device that needs no special logic uses a default manifest-driven codec; a device that needs logic (a learned anchor, stateful decode) supplies a small implementation.
- A registry that resolves a device model string to its manifest and codec, with the rule from the ledger that an unknown or legacy gen5 model string defaults to gen5, and that a 5.0 and an MG are indistinguishable at scan time and must be disambiguated by the registry or model string.

`docs/connectors.md` documents the manifest schema field by field, the `DeviceCodec` contract and its boundaries, and the step-by-step for adding a device (one manifest, optionally one codec crate, no core edits).

**Tests first:**
- `manifest_deserialises_all_fields` — a sample manifest JSON round-trips into the manifest types with every field populated and asserted.
- `registry_defaults_unknown_gen5_model` — an unrecognised model string that belongs to the gen5 family resolves to the gen5 manifest.
- `codec_cannot_reach_storage` — a compile-level guarantee expressed through the trait's signature (the `DeviceCodec` has no storage handle in scope); document the check in `check_deps.py` as the enforcement and assert the manifest-driven default codec produces samples from a frame without any storage dependency.
- `field_layout_unit_conversion_applies` — a field declared with a unit conversion in the manifest is decoded with that conversion applied, asserted against a known value.

**Exit:** `cargo test -p mav-codec`, `cargo clippy -p mav-codec --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`, `tools/check_deps.py`.

**Notes:** The per-device key-value store handle exists in the trait from the start even though the realtime HR slice does not use it, because the WHOOP 4.0 skin-temp anchor (a later milestone) needs it and the trait is easier to freeze correctly now than to widen later. Keep the manifest purely static: no analytic knowledge, no thresholds that belong to a metric. If a value feels like it belongs to an algorithm rather than to the wire format, it does not go in the manifest.

**Status: done.** Decision log: the codec returns `Vec<RawSample>` and the engine wraps it into a `RawSampleBatch`, because the codec does not know its `DeviceId` and handing it one would widen the boundary for nothing. Packet-map semantics: a mapped type whose layout key is absent from `layouts` is known-but-not-decoded and yields no samples and no error (so historical and event packets do not spam the journal before M5); only a type absent from the map entirely is DECODE_UNKNOWN_PACKET_TYPE. Manifests are parsed with `deny_unknown_fields` so a typo fails loudly. Repeats carry a mandatory `max_count` sanity bound, and the manifest-driven decode (fields, counted repeats, drop-zero, linear conversions, the time spec with its per-field subseconds unit) landed here rather than in P4, which now owes only the capture-fixture tests.

## Packet M1-P3: whoop5 realtime manifest and capture fixture

**Owns:** `connectors/whoop5/manifest.json`, `fixtures/capture/whoop5_realtime_hr_v1.jsonl` (the capture), and `fixtures/capture/whoop5_realtime_hr_v1.README.md` (its provenance and confidence).

**Must not touch:** `mav-codec` source (this packet is data that P2's types consume).

**Contract:** A gen5 manifest covering only the realtime subset needed for M1. From `docs/protocol/whoop.md`:
- GATT: service `fd4b0001-cce1-4033-93ce-002d5875f58a`, command (write) characteristic `fd4b0002-…`, notify characteristics `fd4b0003 / 0004 / 0005 / 0007`.
- Frame parameters: start-of-frame `0xAA`, the gen5 8-byte header, CRC-16/Modbus over the header and CRC-32 over the padded payload, payload zero-padded to a 4-byte boundary.
- Packet map: at minimum `40 = REALTIME_DATA`, plus `35 = COMMAND`, `36 = COMMAND_RESPONSE`, with the inner payload layout `[0]=packet_type, [1]=sequence, [2]=subtype, [3..]=body`.
- Field layout for `REALTIME_DATA` at the gen5 offsets (the gen4 offsets plus 4): timestamp `u32` at offset 10, sub-second `u16` at 14, heart rate `u8` at 16, RR count `u8` at 17, and RR intervals as `u16` little-endian starting at offset 18, two bytes each, in milliseconds, with 0-millisecond placeholders dropped.
- Unit conversions: heart rate is whole bpm; RR intervals are whole milliseconds.
- Declared capabilities: `HeartRate` and `RrInterval`.

The capture fixture is a sequence of frames including a `REALTIME_DATA` packet that decodes to a known heart rate and RR set. Its README states where it came from and its confidence tag. Where a surveyed real capture supplies the bytes, cite it; where bytes are constructed to the documented `[XVAL]` layout because no real capture is on hand, say so and tag the fixture provisional until a strap verifies it.

**Tests first:**
- `whoop5_manifest_loads` — the manifest deserialises through P2's types with the fields above asserted.
- `whoop5_manifest_declares_hr_and_rr` — the declared capability set is exactly `HeartRate` and `RrInterval`.
- The capture fixture is consumed by P4's decode test, not by this packet; this packet asserts only that the manifest and fixture files parse.

**Exit:** `cargo test -p mav-codec` (manifest load test), `tools/check_docs.sh` (the fixture README and cross-references resolve).

**Notes:** The offsets here are `[XVAL]` but not hardware-verified; the manifest header comment records the confidence tag so the hardware epoch knows to check them. Pin the exact offsets from the fixture during P4, and if the fixture and these documented offsets disagree, resolve it in the ledger with a note rather than silently editing the number. Generate the fixture through `skills/golden-fixtures`; never hand-edit it afterward.

**Status: partial.** The manifest is written and tested (`core/crates/mav-codec/tests/whoop5_manifest.rs` covers identity, capability set, the documented offsets, and the known-control-packet rule). The capture fixture and its README remain open, blocked on the capture-format decision in P10's `mav-replay` work; do not construct the fixture until the reader exists to consume it.

## Packet M1-P4: Decode stage — REALTIME_DATA to RawSamples

**Owns:** `core/crates/mav-codec/src/decode.rs` (new) and its test module, `fixtures/sample/whoop5_realtime_hr_v1.json` (the expected decoded samples).

**Must not touch:** `mav-frame` (consume its validated frames), the manifest types (consume them), SQI, timeline, store.

**Contract:** The manifest-driven decode: take a validated frame and the whoop5 manifest, read the packet type from the inner payload, and for `REALTIME_DATA` produce a batch of `RawSample`s using the field layout declared in the manifest. One `HeartRate` sample per frame carrying the decoded bpm and the frame's device timestamp, and one `RrInterval` sample per non-zero RR value, each with the frame's device time and a per-second sequence index so the timeline can tell equal intervals apart later. Zero-millisecond RR placeholders are dropped and the drop is not logged as an error (they are expected padding), but any value that fails to decode is logged with a `Decode`-category `MavError` code and reason. An unknown packet type becomes `Unknown(u8)` and is logged, never a panic.

**Tests first:**
- `decodes_realtime_hr_from_fixture` — running the P3 capture fixture through decode yields the samples in `fixtures/sample/whoop5_realtime_hr_v1.json` exactly, heart rate and every RR interval, with device timestamps.
- `drops_zero_ms_rr_placeholders` — a `REALTIME_DATA` payload with 0-millisecond RR entries produces no RR samples for those slots and no error log for them.
- `unknown_packet_type_is_logged_not_panicked` — a frame with an unmapped packet type produces an `Unknown` result and a log entry, and does not panic.
- `rr_samples_carry_sequence_index` — two RR intervals in the same second decode to two samples with distinct sequence indices.

**Exit:** `cargo test -p mav-codec`, `cargo clippy -p mav-codec --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** The per-second sequence index on RR samples is the seed of the dedup fix in P6; without it, two equal RR intervals in the same second collapse into one and bias RMSSD high. Set it here so the timeline has it to key on. Decode reads offsets from the manifest, not from constants baked into this file, so a corrected offset is a manifest edit, not a code change.

## Packet M1-P5: Minimal signal-quality scoring

**Owns:** all of `core/crates/mav-sqi/src/`, `fixtures/sqi/whoop5_realtime_hr_v1.json`. May edit `core/crates/mav-sqi/Cargo.toml` to depend on `mav-model`.

**Must not touch:** decode, timeline, store.

**Contract:** Score raw samples before any normalisation, attaching a `Quality { score, reason }` to each. For M1 the scoring is deliberately minimal and plausibility-based, from the ledger's valid ranges: a heart rate outside roughly 30 to 220 bpm is downscored with a `RejectReason` naming the range; an RR interval outside roughly 300 to 2000 milliseconds is downscored likewise. A sample inside range gets a full score. No sample is discarded at this stage; a poor sample is scored, kept, and carried forward with its reason so the inspector can see it. The output is value plus quality plus reason, never a silent drop.

**Tests first:**
- `in_range_hr_scores_full` — a 60 bpm sample gets a score of 1.0 and no reason.
- `out_of_range_hr_is_downscored_with_reason` — a 300 bpm sample gets a reduced score and a `RejectReason` that names the plausibility bound.
- `out_of_range_rr_is_downscored_with_reason` — a 2500-millisecond RR sample is downscored with a reason.
- `no_sample_is_dropped` — a batch containing out-of-range samples returns the same count it received, all present with quality attached.

**Exit:** `cargo test -p mav-sqi`, `cargo clippy -p mav-sqi --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** SQI runs on raw signals before normalisation on purpose, because quality of the raw reading is what we want to know, not quality of a value we have already cleaned up. The ranges are approximate and provisional; they are thresholds owned by SQI, not by the manifest, since they are analytic judgement rather than wire format.

## Packet M1-P6: Timeline insert and RR dedup with sequence tiebreaker

**Owns:** all of `core/crates/mav-timeline/src/`, `fixtures/timeline/whoop5_realtime_hr_v1.json`, `fixtures/timeline/rr_dedup_v1.json`. May edit `core/crates/mav-timeline/Cargo.toml` to depend on `mav-model` and add `proptest` as a dev dependency.

**Must not touch:** store, features.

**Contract:** Order samples by time, deduplicate them, and prepare them for storage without ever interpolating or mutating a raw device timestamp. The dedup key for RR intervals is `(device, timestamp, rr_ms, seq)`, where `seq` is the per-second occurrence index attached in P4. This is the one that history got wrong: without the `seq` tiebreaker, two equal RR intervals in the same second collapse to one, a zero-difference beat vanishes, and RMSSD and HRV bias high at rest and during sleep. Clock correction for M1 is limited to the plausibility check: use the device timestamp only if it falls in a plausible window, otherwise fall back to the capture wall-clock time and flag the sample; the correction is stored as a mapping, and the raw timestamp is left untouched.

**Tests first:**
- `equal_rr_in_same_second_are_kept_distinct` (invariant) — two equal RR intervals in the same second with different `seq` values survive dedup as two samples; keying without `seq` would collapse them, and the test asserts the count is two. This is the codified lesson from the surveyed lineage.
- `exact_duplicate_is_deduped` — two samples identical in all key fields including `seq` collapse to one.
- `implausible_timestamp_falls_back_and_flags` — a sample whose device timestamp is outside the plausible window is stored against capture time and carries a flag, with the raw timestamp preserved.
- `ordering_is_stable` (proptest) — for any shuffled batch of samples, the timeline output is ordered by time and the multiset of surviving samples is independent of input order.
- `raw_timestamp_never_mutated` — after clock correction, the sample's raw device timestamp equals its input value.

**Exit:** `cargo test -p mav-timeline`, `cargo clippy -p mav-timeline --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** Timeline dedup is on the property-test-mandatory list in `docs/testing.md`. The `seq` tiebreaker test is the single most load-bearing assertion in M1's data correctness, so write it first and watch it fail with a `seq`-less key before you add `seq`. Cite the invariant in `docs/pipeline.md`.

## Packet M1-P7: `mav-store` append-only schema and migrations

**Owns:** all of `core/crates/mav-store/src/`, `docs/storage.md`, migration files under `core/crates/mav-store/migrations/`. May edit `core/crates/mav-store/Cargo.toml` to depend on `mav-model` and `rusqlite` (bundled).

**Must not touch:** timeline, features, analytics.

**Contract:** A single SQLite database in WAL mode with forward-only, numbered migrations applied at open, gated by a schema-version pragma; opening a database whose schema is newer than the code understands is refused rather than silently upgraded. The M1 schema: an append-only samples table keyed to make re-sync idempotent (insert-or-ignore on the natural key including the RR `seq`), a provenance table keyed by `MetadataId` recording source stream, quality, algorithm id, algorithm version, and sample count, and the error-journal table that `docs/errors.md` promised in M0 (the ring buffer's durable sibling). Derived tables are rebuildable from raw plus versions; the round-trip rule holds, so dropping and recomputing derived data must reproduce identical values.

**Tests first:**
- `migrations_apply_from_empty` — opening a fresh database applies all migrations and reports the expected schema version.
- `refuses_newer_schema` — opening a database whose schema-version pragma exceeds the code's known version fails with a `Storage`-category error rather than migrating.
- `sample_insert_is_idempotent` — inserting the same sample twice, including identical `seq`, results in one row.
- `distinct_seq_samples_both_persist` — two RR samples differing only in `seq` both persist, matching the timeline invariant.
- `provenance_links_metric_to_source` — a provenance row round-trips with its source stream, algorithm id, and version.

**Exit:** `cargo test -p mav-store`, `cargo clippy -p mav-store --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** The idempotent insert on the natural key is what makes a re-sync safe: streaming the same capture twice must not double the data. Keep raw evidence append-only; never update a raw sample row. The three-tier pattern (append-only raw, regenerable decoded, recomputed rollups) is documented in `docs/storage.md` and matches the surveyed convention.

## Packet M1-P8: Heart rate feature

**Owns:** `core/crates/mav-feature/src/hr.rs` (new) and its test module, `fixtures/feature/whoop5_realtime_hr_v1.json`. May edit `core/crates/mav-feature/Cargo.toml` to depend on `mav-model` and `mav-store`.

**Must not touch:** analytics, snapshot, FFI.

**Contract:** Compute the minimal HR features the M1 snapshot needs: the current (most recent, in-range) heart rate and a session summary (count, and mean or last of the in-range samples over the session window). Each feature carries a `MetadataId` linking to its provenance row, and declares an `ALGORITHM_VERSION`. Out-of-range samples (those SQI downscored below a threshold) are excluded from the summary but remain visible in the store; the feature records how many it excluded and why.

**Tests first:**
- `current_hr_is_latest_in_range` — given a sample series ending with an out-of-range spike, the current HR is the latest in-range value, not the spike.
- `session_summary_counts_in_range_only` — the summary count excludes downscored samples and records the excluded count.
- `feature_carries_provenance` — the feature's `MetadataId` resolves to a provenance row naming its source stream and algorithm version.
- `feature_matches_fixture` — the features computed from the pipeline fixture equal `fixtures/feature/whoop5_realtime_hr_v1.json`.

**Exit:** `cargo test -p mav-feature`, `cargo clippy -p mav-feature --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** This is a feature, not a metric; it stays deterministic and simple. It lands under the admission rule because it has a golden fixture derived from the capture, which is exactly the bar `docs/testing.md` sets.

## Packet M1-P9: Snapshot and FFI query

**Owns:** `core/crates/mav-engine/src/snapshot.rs` (new), the snapshot additions to `core/crates/mav-ffi/src/`, `fixtures/snapshot/whoop5_realtime_hr_v1.json`. May edit `mav-engine` and `mav-ffi` `Cargo.toml` for the dependencies each needs.

**Must not touch:** the acquisition file (P1 owns it), the decode and feature internals (consume their outputs).

**Contract:** Assemble the "current HR plus session summary" snapshot as an immutable read model, and expose it over FFI. The snapshot type is serde-serialisable and carries the current heart rate, the session summary, and enough provenance ids that a caller could walk back to the underlying samples. Add the FFI query that returns the current snapshot, and add `run_fixture(fixture_id) -> canonical JSON + hash` from `docs/testing.md`, which runs a named fixture through the full pipeline and returns the canonical snapshot JSON together with a stable hash of it. The canonical form is deterministic: fixed field order, fixed number formatting, so the hash is reproducible across platforms.

**Tests first:**
- `snapshot_matches_fixture` — the snapshot assembled from the pipeline equals `fixtures/snapshot/whoop5_realtime_hr_v1.json`.
- `run_fixture_hash_is_stable` — calling `run_fixture` on the same fixture twice returns the identical hash.
- `snapshot_serialisation_is_canonical` — serialising the snapshot produces byte-identical output across repeated runs, with field order and number formatting fixed.
- `snapshot_carries_walkback_ids` — the snapshot's ids resolve back through provenance to the source samples.

**Exit:** `cargo test -p mav-engine`, `cargo test -p mav-ffi`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check`, `tools/check_docs.sh`.

**Notes:** The canonical serialisation is the linchpin of the parity exit criterion; if two platforms format a float differently, the hashes diverge and the exit fails for a reason that has nothing to do with the pipeline. Nail the canonical form here. `run_fixture` is the mechanism the parity harness in P11 drives.

## Packet M1-P10: `mav-replay` drives the pipeline end to end

**Owns:** all of `core/crates/mav-replay/src/`. May edit `core/crates/mav-replay/Cargo.toml` to depend on the crates it orchestrates.

**Must not touch:** the internals of the stages; `mav-replay` composes them, it does not reimplement them.

**Contract:** A binary that reads a capture file, feeds its bytes through the full pipeline (acquisition, reassembly, decode, SQI, timeline, store, features, snapshot), and dumps every stage boundary to JSON via the `Tap`. Running it on the M1 capture fixture reproduces the same canonical snapshot and hash that `run_fixture` produces. This is the primary hardware-free development and fixture-generation tool, and it is how a human or an agent inspects what each stage did without a strap.

**Tests first:**
- `replay_reproduces_snapshot_hash` — replaying `fixtures/capture/whoop5_realtime_hr_v1.jsonl` yields the same canonical snapshot hash as `run_fixture` on the same fixture.
- `replay_dumps_every_boundary` — the replay output contains a section for each pipeline stage in order, asserting the stage names and that counts are present.
- `replay_logs_rejections` — a capture containing a corrupt frame produces a boundary dump that includes the rejection with its error code, and the run still completes.

**Exit:** `cargo test -p mav-replay`, `cargo run -p mav-replay -- fixtures/capture/whoop5_realtime_hr_v1.jsonl` produces the expected snapshot and hash, `cargo clippy -p mav-replay --all-targets -- -D warnings`, `cargo fmt --check`.

**Notes:** `mav-replay` is the substitute for hardware until the straps arrive, so its output is meant to be read by a person debugging a decode. Keep the boundary dump legible. This packet ties the whole slice together in one command, which is why it comes near the end.

## Packet M1-P11: Cross-platform parity harness

**Owns:** the iOS test harness under `apps/ios/` and the Android test harness under `apps/android/` that call `run_fixture`, and a short parity section in `docs/testing.md`.

**Must not touch:** the core crates; this packet exercises the FFI, it does not change what is behind it.

**Contract:** A test on each platform that links the core through the M0 bindings, calls `run_fixture("whoop5_realtime_hr_v1")`, and asserts the returned hash equals the known-good hash. The two platforms run the same fixture and must produce the same hash; a difference is a binding bug by definition, since the core is shared. Document in `docs/testing.md` that any platform divergence is a binding defect and how to run the two harnesses.

**Tests first:**
- iOS: `parity_whoop5_realtime_hr` — the simulator test calls `run_fixture` and asserts the canonical hash.
- Android: `parity_whoop5_realtime_hr` — the emulator test calls `run_fixture` and asserts the same canonical hash.
- A recorded known-good hash that both harnesses compare against, generated once from `run_fixture` and checked into the fixtures.

**Exit:** both platform tests pass on their simulators, returning the identical hash, which is the M1 exit criterion.

**Notes:** This is the packet that proves the central architectural bet: one core, two thin shells, identical numbers. If the hashes differ, do not adjust one platform to match the other; find the non-determinism (almost always number formatting or field order in the canonical serialisation from P9) and fix it at the source. The single shared Rust core is what removes the whole class of iOS/Android divergence that the surveyed codebases suffered; this harness is what proves it stayed removed.

## M1 exit

M1 is done when the iOS and Android simulator parity tests both call `run_fixture("whoop5_realtime_hr_v1")` and return a byte-identical snapshot hash, with the full workspace and docs gates green. When that holds, this file moves to `docs/plans/completed/M1.md` with a retro: what surprised us in the first real slice, what drifted, and which doc or ledger fixes were filed, particularly any realtime-layout offset that wants hardware confirmation in the hardware epoch.

# ADR-012 — Frame parameters become manifest data

## Context

Milestone 2 challenged the connector abstraction with an adversarial frame description unlike
WHOOP: a different start-of-frame, a big-endian length, a single CRC-8 trailer, no header CRC, and
no padding. The exercise surfaced a real limit in the design that shipped in Milestone 1.

In M1, the core reassembles incoming bytes using a reassembler selected by the manifest's
`frame.wire_format`, which is a closed enum of exactly `gen4` or `gen5`, and only then hands the
`DeviceCodec` an already-validated `RawFrame`. Two consequences follow, and together they make a
non-WHOOP frame format impossible to express:

- The manifest cannot describe custom framing. `frame.wire_format` accepts only `gen4` or `gen5`,
  and `Manifest::validate` rejects anything else.
- The codec cannot own its framing either, because `DeviceCodec::decode` receives a `RawFrame` the
  core already produced; a codec never sees raw bytes.

M1 hardcoded the two WHOOP wire formats because at that point there were only two, and the pair was
enough to ship the first slice. That was the right call for M1 and the wrong shape to keep, which is
exactly the kind of thing a second device is meant to reveal. This is the milestone failing early
rather than a workaround being found, per the M2 preamble.

## Decision

Frame parameters become data in the manifest, and the reassembler becomes driven by that data rather
than by a closed enum. A device declares its framing as a small structured record: the start-of-frame
byte, the length field (its offset, width, endianness, and whether it counts the trailer), the header
CRC if there is one (kind and the byte range it covers), the trailer CRC (kind and range), and the
padding rule. `mav-frame` gains a reassembler that takes such a description; `gen4` and `gen5` become
two named presets expressed in exactly that form. Adding a device with a new
frame format is then a manifest change and nothing more, which keeps the promise that a connector is
data plus, at most, a small codec for the logic data cannot express.

Framing stays declarative rather than moving into the codec, because a start-of-frame byte, a length
field, and a CRC are structural facts about the wire, which is the definition of what belongs in a
manifest (ADR-007). The codec keeps holding only what data genuinely cannot express.

## Consequences

`mav-frame`'s `WireFormat` enum and its `Reassembler` and `build_frame` are reworked to take a frame
description, and `mav-codec`'s `FrameConfig` grows from a wire-format string into that description
with `gen4` and `gen5` as presets. `mav-engine`'s pipeline reads the description from the manifest
instead of matching on two strings. The existing frame fixtures and property tests carry over
unchanged in intent, because gen4 and gen5 must decode exactly as before; the presets are verified
against the same captured hello frame. This is a deliberate, planned core change enabled by an ADR,
which is different from the forbidden thing, a device-specific edit slipped into the pipeline to make
one device work.

The cost is a more involved frame schema and a reassembler that interprets a description instead of
branching on a known format, which is marginally slower and more code. That is the right trade: the
whole point of the connector system is that device number three, and the cloud connector in M7, do
not get to force a core edit, and a hardcoded pair of formats would have forced one the first time a
device framed its bytes differently.

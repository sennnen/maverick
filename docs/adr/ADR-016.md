# ADR-016 — Device codec crates: WHOOP moves out of the core

## Context

ADR-011 draws the boundary in one sentence: `mav-codec` never learns about any specific device.
connectors.md states the test for it: if adding a device requires touching a crate under `core/`,
the abstraction has failed. By mid-2026 the codebase failed that test in four places, all inside
`mav-codec`:

- `records.rs` carried seven WHOOP historical-record decoders (`r20_k18`, `r20_k26`, `gen4_v24`,
  `gen4_v5`, `gen4_v25`, `gen5_v20`, `gen5_v21`).
- `events.rs` carried the WHOOP event vocabulary.
- `control.rs` carried the WHOOP historical-control layouts (COMMAND_RESPONSE 0x24, METADATA 0x31,
  the HISTORY_END cursor range).
- `commands.rs` carried the WHOOP alarm and haptic command builders, opcodes and all.

Each arrived under the honest banner of a "reviewed module the manifest can only name": the
layouts genuinely cannot be expressed in the manifest DSL (a version byte or an event number
selecting among body layouts is dispatch, not data), and the admission rule (ADR-009) demands a
reviewed module somewhere. But "somewhere" kept resolving to `mav-codec`, and each addition made
the next one look more normal. A second device family with its own record versions would have had
to edit the core again.

The root cause is structural, not sloppiness. The `DeviceCodec` trait and the registry existed
from ADR-007, but nothing at runtime ever used them: the pipeline hardcoded `ManifestCodec`, and
`install_connector` parsed manifests without ever resolving a codec. Meanwhile ADR-011 made the
connectors repository data-only, which it must be — a phone cannot load compiled code at runtime,
so a codec can never travel with a manifest. Device logic that data cannot express therefore had
no home, and it accreted in the one crate that was supposed to be forbidden to hold it.

A fifth, smaller instance lived in `mav-frame`: outbound frame building was two hand-rolled
WHOOP-only functions, even after ADR-012 made inbound framing data-driven. That was corrected
separately by making the outbound builder `FrameSpec`-driven (padding rule and header template as
data), and this ADR assumes it.

## Decision

Device codecs are compiled crates under `core/connectors/`, one per family, named
`mav-connector-<family>`. The first is `mav-connector-whoop`, which absorbs `records.rs`,
`events.rs`, `control.rs`, and `commands.rs` wholesale and implements the `DeviceCodec` trait
(delegating everything the manifest DSL *can* express to `ManifestCodec`).

The seam that was missing gets built, in three pieces:

- **The manifest names its codec.** A new optional `codec` field carries the id (`"whoop"`).
  Naming `record_versions` or an `event_vocabulary` without naming a codec is a validation error,
  because nothing in the core can decode them.
- **The edge registers codec factories.** `HostRuntime::register_codec(id, factory)` is called by
  the crates that assemble the pipeline — `mav-ffi` at startup, `mav-replay` per run — for each
  connector crate the binary links. The engine resolves a manifest's `codec` id against exactly
  that set; an unknown id refuses to install with `DECODE_CODEC_UNAVAILABLE` (3006). The engine
  itself never names a device.
- **Decoder ids are checked where manifest and codec meet.** `DeviceCodec` gains
  `admitted_record_decoders()` and `admitted_event_vocabularies()`; install validates the
  manifest's named ids against the codec's lists, so a name/module mismatch fails at install
  rather than silently decoding nothing.

The dependency rules extend mechanically (`tools/check_deps.py`): a connector crate may depend
only on `mav-model`, `mav-frame`, and `mav-codec` — it cannot reach storage, analytics, the
engine, or another connector — and only `mav-ffi` and `mav-replay` may depend on a connector
crate. `mav-engine` may use one in dev-dependencies to exercise the registration seam in tests,
which check_deps deliberately ignores.

ADR-011 is amended, not reversed. Manifests — the updatable, reviewable data — still live in the
`sennnen/maverick-connectors` repository and still cannot destabilise the core. What this ADR
fixes is the half ADR-011 left unplaced: the compiled residue that data cannot express. That
residue must be linked into the binary, so it lives in this repository, but outside `core/crates/`
and boxed behind the one trait, where the build graph — not good intentions — keeps it from
touching anything else. The standard-profile decoders (`standard.rs`) stay in `mav-codec`: they
are open Bluetooth SIG profiles, the same exception ADR-011 already carved out.

## Consequences

Adding a device family is now: a manifest in the connectors repository, plus (only if the DSL
cannot express the whole decode) one `mav-connector-<family>` crate here and one `register_codec`
line at each of the two edges. No core crate changes. The claim is enforced: check_deps fails on
any new edge, and the whole WHOOP eviction shipped without changing a single decode result —
every golden fixture, parity hash, and frozen snapshot is byte-identical before and after.

The costs are accepted: a new device codec still means an app release (unavoidable for compiled
code on iOS); the two edge crates each carry a small id-to-factory table that must list every
built-in connector crate; and `mav-codec` keeps the trait, the manifest schema, and the registry
while owning no device knowledge — which is exactly the shape ADR-007 described and the runtime
now actually uses.

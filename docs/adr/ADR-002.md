# ADR-002: A synchronous typed pipeline, not event buses

## Context

The plan Maverick grew out of specified six publish/subscribe buses between processing stages.
Pub/sub hides call order: what runs, and in what sequence, becomes a property of the subscription
list at runtime rather than of anything readable on the page. Replay stops being deterministic,
debugging becomes archaeology, and, for a codebase written by an agent swarm, buses are where
spaghetti forms fastest, because each agent can add a subscriber and no agent owns the flow.

## Decision

Data moves through a synchronous typed call graph. Every stage is a function
`fn run(input: StageIn, ctx: &mut StageCtx) -> Result<StageOut, MavError>`, with the boundary types
frozen in mav-model and the call order written explicitly in mav-engine. Async exists in exactly
one place: a bounded channel from the native BLE layer into the pipeline entry. Inspectability
comes from the Tap trait, invoked at every stage boundary with counts and ids.

## Consequences

Execution order is the order written in the engine, so feeding the same bytes twice does the same
work in the same order, which is what makes mav-replay a faithful reproduction tool rather than an
approximation. The Tap gives the visibility a bus would have given without surrendering
determinism. The cost is that fan-out must be explicit in the engine rather than emergent, and
long-running work must be scheduled by the engine's triggers rather than fired off a topic. Both
costs are the point: everything the pipeline does is written down somewhere an agent can read.

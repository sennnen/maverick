# ADR-031: Connectors declare their own device controls

## Status

Proposed.

## Context

[ADR-030](ADR-030.md) gave the user one lever over a connected device — battery saver — and made it a
host policy the connector obeys. That shape was right, and it does not generalise. Every knob a
device actually has is connector knowledge: whether the MG's console characteristic is worth its
battery, whether a raw AFE capture should be open, which of a strap's several history cadences to
use. The host cannot enumerate those, because enumerating them means the host knows what devices
exist, which is precisely what [ADR-017](ADR-017.md) removed.

The obvious workaround is worse than the problem. If each new knob needs a new `EventBody` variant, a
new host toggle, and a new app release, then adding a device *feature* rebuilds Maverick even though
adding a *device* does not. That is the bundled-driver failure with a smaller blast radius.

The other obvious shape — let a connector hand the host a blob of UI — is rejected outright. A
connector is hostile by assumption. It gets no filesystem, no network, and no radio; it does not get
to draw either.

## Decision

A connector may **declare** a bounded set of typed controls in its manifest. The host renders them
from its own components, in its own design language, and sends the resulting value back as an event.

- A control is one of three kinds: `toggle` (bool), `choice` (one of a declared, bounded set of
  string options), or `action` (fire-and-forget, no stored value).
- Each declares a stable `id`, a `label`, a one-line `explanation`, an optional `experimental` flag,
  and a default. Text is bounded and sanitised on the same path as every other manifest string.
- Declarations are validated at inspection time, before approval, and appear in the approval report
  alongside capabilities. A user approving a connector has already seen every control it can ask for.
- Setting one delivers `EventBody::DeviceControlSet { id, value }` and persists the value in
  connector-scoped state. Non-default values are restated on activation and resume, the same
  discipline ADR-030 applies to low power, so a connector's behaviour stays a pure function of the
  events it has seen.
- Control ids live in the connector's namespace and may not collide with a host-owned id. Battery
  saver stays host-owned: it is a user preference about the phone as much as the strap, and a
  connector that could decline to declare it could hide it.

The host renders labels and explanations as **data**, never as markup or format strings, and never
grants a control any capability beyond the event it emits. A control cannot request a permission,
open a stream the manifest did not already declare, or change the trust decision the user made.

## Consequences

- Adding a device feature is a connector release, not a Maverick release. That closes the last case
  where the app binary had to change for a device reason.
- The manifest gains a section and therefore a validation surface: count, id, label, option-set, and
  aggregate byte limits are declared with the other artifact limits and enforced before
  instantiation. An artifact without the section is unchanged, so every signed artifact stays valid
  and the ABI minor does not move.
- `host-snapshot` gains a `device-controls/v1` block. Its canonical fixture is re-blessed once; the
  block is empty for every existing connector, so no other fixture changes.
- The user-facing risk is a connector shipping a control whose explanation lies about what it does.
  That is the same risk as a connector lying about its capabilities, mitigated the same way — the
  declaration is signed, visible before approval, and revocable — and it is not made worse by
  rendering it.
- Deliberately excluded: numeric sliders, free text, nested groups, and any control that changes
  during a session. All four invite a connector to drive the interface instead of describing itself,
  and none has a device knob today that needs them.

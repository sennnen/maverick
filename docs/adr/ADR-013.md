# ADR-013 — One stateful host runtime beside the stateless fixture runner

## Context

The first UniFFI surface accepts a whole manifest and capture, runs them through an in-memory store,
and returns canonical snapshots. That is the right shape for fixtures and parity. It is the wrong
shape for a live app: replaying an ever-growing JSON capture for every BLE notification would repeat
work, lose persistent session state, and push ordering decisions into Swift and Kotlin.

Exposing every pipeline stage separately would avoid the repeated replay, but it would make the
native shells responsible for stage order, storage transactions, retries, and snapshot publication.
That recreates the cross-platform divergence the shared core exists to remove.

## Decision

Keep the stateless fixture runner and add one stateful UniFFI `MavRuntime` object for product use.
The runtime owns the store, connector registration, acquisition state, pipeline state, bounded
transport-action queue, and immutable host snapshot. Native code feeds a closed set of transport
events and executes a closed set of transport actions. It cannot call pipeline stages, query the
database, synthesize commands, or acknowledge historical data on its own.

Mutation is serialized inside the runtime. Hosts call it from a dedicated background executor.
Versioned canonical JSON remains the read-model boundary because it gives Swift and Kotlin one
schema, one frozen fixture, and an additive compatibility path. UniFFI records carry the JSON, hash,
and revision; pipeline types do not cross.

The full method, event, action, snapshot, threading, and compatibility contract lives in
[platform.md](../platform.md).

## Consequences

Live input and offline replay use the same core order without making a platform rebuild the
pipeline. Persistent state survives app restarts. Retry and historical-ack safety remain one Rust
implementation. The bounded action queue gives backpressure a visible failure mode instead of
allowing silent loss.

The runtime is more stateful code to test, and synchronous database work means hosts must keep it
off the UI thread. Polling by snapshot revision is less immediate than callbacks, but it avoids
UniFFI re-entrancy and is easier to reason about across app lifecycle changes. The stateless runner
remains because it is still the simplest and strongest parity harness.

# ADR-021 — Two layers of deduplication, one of them bounded

Status: accepted.

## Context

`Timeline` deduplicates on `(kind, device_time, value bits, seq)` and deliberately keeps its dedup
memory across `drain_ordered`, so a re-sync arriving after a drain is still recognised. One Timeline
lives for a whole connector session.

Those two facts together are unbounded. M5 shipped historical sync: a multi-day backfill pushes every
banked sample through one session's Timeline, and the set holds a key for each. Nothing evicts.

The store already deduplicates durably on its natural key — `INSERT OR IGNORE` — and that layer is
the one that must be correct, because it is the one that survives a restart.

## Decision

The timeline's dedup set becomes a **window**: a `HashSet` for lookup plus a `VecDeque` for
oldest-first eviction, `Timeline::with_window(max_keys)`, defaulting to 65,536 keys. The window is
the fast path, not the source of truth. A duplicate that arrives after its key has been evicted is
accepted by the timeline and rejected by the store, which is why LP-P2 had to surface the store's
insert outcome into commit accounting rather than discarding it.

Eviction never drops a sample. It drops the *memory* of a sample, and only samples already drained.

## Consequences

Session memory is bounded by the window rather than by how much history a device banked. The cost is
that a cross-window duplicate reaches the store instead of stopping at the timeline — one extra
`INSERT OR IGNORE` per stale sample, which is what the store's natural key exists for.

The window size is a memory/redundant-write trade-off, not a correctness knob: any value keeps the
persisted result identical, because the durable layer is unchanged. 65,536 covers far more than any
single re-sync burst repeats within.

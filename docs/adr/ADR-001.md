# ADR-001: One shared Rust core, thin native bindings

## Context

Maverick targets iOS and Android with identical behaviour: the same strap must produce the same
data on both phones. Two prior codebases in this lineage implemented the decode path twice, once in
Swift and once in Kotlin, and both accumulated parity bugs. In one, the Android reassembler handled
only the gen4 frame format while iOS handled both, so the same device yielded different data
depending on the phone. This class of bug recurs every time a decode detail changes on one platform
and not the other, and each platform looks internally consistent while it happens.

## Decision

All decoding, analytics, storage, and orchestration live in a single Rust workspace, compiled once
and exposed to both platforms through UniFFI. The native shells own only what a shared library
cannot: the BLE radio and (when a model exists) ML inference. Everything else is Rust.

## Consequences

The two-implementations class of parity bug is removed by construction: there is one reassembler,
one CRC, one timeline, and a defect in any of them is at least the same defect everywhere. The
remaining divergence surface is the thin bindings, and the fixture-hash parity harness
(docs/testing.md) checks that mechanically; a hash mismatch is a binding bug by definition. The
cost is a Rust toolchain in both app builds, an FFI layer to maintain, and the two native seams
(radio, inference) that must be kept deliberately small. We accept those costs; the prior codebases
paid far more for the alternative.

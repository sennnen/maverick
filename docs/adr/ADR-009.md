# ADR-009: Algorithms admitted only with a golden fixture or published reference

## Context

One surveyed codebase carried roughly forty speculative analytics engines whose "golden" tests
proved only that Swift, Kotlin, and a stored reference generated by the same code all agreed:
self-consistency, not physiological validity. A formula wrong on both platforms passes such tests
forever. The original Maverick plan inherited the ambition to build a large algorithm catalogue
upfront, which is how a swarm ends up producing exactly that kind of always-green speculative code.

## Decision

An algorithm lands in the codebase only when it has (a) a golden fixture derived from a real
capture or a published reference implementation, or (b) property or invariant tests that can
genuinely fail. Anything that clears neither bar stays an explicit stub, reported by capability
negotiation as unavailable. Additionally, a metric is called validated only when checked against
ground truth or a published reference; a metric that merely agrees with itself across platforms is
consistent, and is labelled provisional wherever it surfaces.

## Consequences

There is no speculative analytic code to maintain, and no test suite that is green because it
cannot be red. The catalogue grows at the pace evidence arrives, which is slower than the prior
codebases grew and considerably more honest. Users and agents can see the difference between a
validated number and a provisional one, and stubs are visible work items rather than hidden gaps.
The cost is restraint: an agent with a plausible formula and no fixture must park it, and the
admission bar, not enthusiasm, decides when it lands.

# ADR-028 — Clock placement is not a quality judgement

Status: accepted.

## Context

`Quality` carried `RejectReason::ImplausibleTimestamp`, and `place_on_wall_with` set it on every
sample whose device clock it had to correct. Two different facts were being written into one field:
*was this value believable* and *do we trust the clock it came with*.

The consequences were not theoretical. `mav-ffi::bounded_sample` dropped any sample with a reason
set, so every clock-corrected reading was invisible to both apps — the entire `ClockMap` apparatus
computed the right answer and the app then threw it away. And because the field held one reason,
setting the placement flag overwrote whatever the signal-quality stage had decided, so a sample that
was both implausible *and* badly timed reported only the timing.

`Quality` could also reach states its own constructors could not produce: score 1.0 with a reason.

## Decision

`Sample` carries a `Placement` instead of an `Option<WallTime>`:

```rust
enum Placement { Unplaced, DeviceClock(WallTime), Corrected(WallTime), CaptureFallback(WallTime) }
```

The instant lives inside the variant, so a wall time without an account of where it came from is
unrepresentable. `RejectReason::ImplausibleTimestamp` is removed; `Quality` is now only about the
value. The FFI gate becomes `Quality::is_usable`, one definition of "usable" shared by every
consumer.

## Consequences

A frozen-interface change to `mav-model`, and a storage migration: the sample table gains a
`placement` column and the reject reason loses a variant. The v1 rows cannot say whether a flagged
sample was corrected or fell back — that distinction was never recorded — so they migrate to
`CaptureFallback`, the weaker claim, which does not assert that the gaps between samples survived.

Clock-corrected samples now reach the apps, which is the bug this fixes.

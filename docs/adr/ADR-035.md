# ADR-035: A model zoo behind one native inference boundary

Status: accepted

## Context

Maverick's ML boundary was designed around one model. [ml.md](../ml.md) set the rule — Rust owns
everything up to the tensor, the platform runtime owns the tensor call — and the provisional
`nao_full_v2` ECG classifier was the single instance of it. The plumbing matched: one Swift class
with one model name baked in, one Kotlin class with one asset path, one pair of hashes in
`ecg_capture.rs`, and an asset gate that asserted *exactly one* model per platform.

Maverick then had a trained model library to bring in: sleep staging from interbeat intervals, PPG
encoders, activity detection and segmentation, awake heart-rate and daytime HRV imputation, energy
expenditure, illness likelihood, cardiovascular age. All in-house, all consuming streams Maverick's
connectors already decode. The question was never whether one of them was worth wiring; it was what
the code should look like when there are many.

Copying the ECG pattern per model would have meant nineteen Swift classes, nineteen Kotlin classes,
nineteen pairs of hand-typed hashes, and nineteen chances for a hash in the code to stop matching
the artefact in the bundle.

Two further facts shaped the decision.

Each checkpoint leaves training as a TorchScript wrapper — validation, resampling, filtering,
windowing, the network, post-processing, all in one archive — and the wrapper's behaviour is
data-dependent: how many pulse feet were found, how many windows the signal produced, how long a
median filter ran.

And the two platform converters fail on different things. Neither the Core ML TorchScript frontend
nor LiteRT's `torch.export` path can convert every core, and the sets they can convert are not
nested.

## Decision

### 1. Convert the neural core, port the wrapper

For each admitted model only the tensor-in / tensor-out neural core is converted. Everything around
it — validators, detrend chains, pulse-foot detection, normalisation, feature vectors — is ported
to deterministic Rust in `mav_analytic::model_zoo`.

This is not a new rule; it is the rule ml.md already stated, applied at scale. Converting a whole
wrapper would freeze data-dependent behaviour into a static graph, producing a model that is
correct for the one signal it was traced on and quietly wrong for every other. It would also put
the resample-off-by-one class of bug inside an opaque binary that two platforms compile
differently, which is precisely what the boundary exists to prevent.

### 2. One registry, generated, three languages

`artifacts/models/manifest.json` is the single source of truth: slug, tensor shapes and dtypes,
algorithm id and version, per-platform artefact hashes, conversion parity, standing and licence.
`tools/ml/generate_bindings.py` renders it into three files that are never hand-edited:

- `core/crates/mav-analytic/src/model_zoo/registry.rs`
- `apps/ios/Maverick/Model/MavModelCatalog.swift`
- `apps/android/app/src/main/java/com/sennnen/mav/ml/MavModelCatalog.kt`

A stale generated file fails CI. The failure mode this removes is real: a re-conversion changes an
artefact, and the hash the admission gate checks still describes the old one.

### 3. A pull-based queue, not one class per model

`mav_engine::model_host::ModelHost` is an addressable queue. Core code enqueues a validated request
and gets an id; the platform polls for work, runs one tensor call, and submits the result with the
hash of the artefact it loaded. Each platform has exactly one runner, `MavModelRunner`, that binds
named float buffers to whichever model the request named.

Pull-based, matching the connector transport seam, because only the platform knows whether the app
is foregrounded and whether the accelerator is free. Synchronous and bounded, because an
uncollected queue of `pulse_ppg` inputs is a memory bug that would surface far from its cause.

### 4. Both platforms or neither

`tools/ml/build_manifest.py` drops any model that converted on only one platform, records the
converter's error under `not_shipped`, and copies through only the rest. This is the repository's
existing parity rule applied mechanically rather than by discipline.

### 5. Two gates, and the second is the one that matters

Every artefact is half-width storage over full-width arithmetic, so deviation from the float32
PyTorch reference is expected rather than suspicious: it is bounded at 1e-2 and **recorded**. What is
gated tightly is whether the two platforms agree with each other — within 5e-3, and measured under
3e-3 across every model. A shared Rust core reading a platform-dependent number is the failure this
repository exists to avoid; matching an fp32 reference exactly is not.

The cross-platform gate was not in the first draft, and it exists because of what happened without
it. Three sleep models converted, hashed cleanly, and reported *exact* parity while their Android
artefacts were wrong by whole logits: the parity measurement was reading the converter's handle on
the source module rather than the written flatbuffer, and LiteRT's nearest-neighbour resize
disagrees with PyTorch whenever it downscales. Comparing the two shipped artefacts to each other is
the check that would have caught it first.

Parity is measured over five probes, not one. Three artefacts passed a single-probe gate and then
disagreed by up to 6e-3 on inputs the pipeline had never tried; `activity_detection` passed at three
probes and missed at five. All of these defects and their fixes are recorded in [ml.md](../ml.md).

### 6. Half-width storage everywhere; half-width arithmetic where it is measured to hold

Every artefact stores constants above 1,024 elements at float16, on both platforms and under every
precision policy. That part is unconditional: it halves the bundle and, because `fp16_align` rounds
the weights on the PyTorch module before either converter runs, both platforms carry bit-identical
weights rather than each rounding whatever its own converter happened to fold.

Arithmetic is decided per model, by measurement, because the two available answers are not
symmetric. Full-width arithmetic looks like the safe default and is not: the Neural Engine is
half-precision hardware, and `MLComputePlan` reports that under a full-width policy **zero**
operations in the entire zoo are assigned to it. Choosing float32 for accuracy silently chooses no
accelerator, and no parity number says so, because parity does not measure where the work ran.

So `coreml_precision.py` runs a ladder — every operation half width, then accumulations exempted,
then transcendentals too, then full width — and a model takes the first rung that clears its parity
bar **and** leaves work on the accelerator. The second condition is the one that had to be measured,
because exempting a few operations partitions some graphs cleanly and takes others off the
accelerator entirely. `sleepnet_bdi` keeps 99 of 182 operations on the Neural Engine under the
exempted policy; the PulseNet encoder keeps 105 of 106 under plain half and *none* under the
exempted one, which is where full width already lands with less error. Nothing in the op list
predicts which, so the plan decides per model.

Most models that end up at full width were never going to be accelerated: `half` was assigned zero
operations for them as well, and the backend does not change with the arithmetic either, so full
width costs nothing and buys back an order of magnitude of accuracy. Two models genuinely trade the
accelerator for accuracy — the PulseNet encoder, whose depth does not survive half-width
accumulation, and `awhr_imputation`, which misses the bar at 1.01e-2 against 1.00e-2, about 2 bpm on
an imputed heart rate. Both trades are recorded per model rather than made globally.

Half-width arithmetic is not free where it applies. The Neural Engine accumulates at half width
where Core ML's CPU path accumulates at full width, so a deep encoder sits further from its float32
reference on the accelerated path than on the CPU. Parity is measured through `ComputeUnit.ALL` for
that reason, and the models whose architecture does not survive it — PulseNet's EfficientNet1D
encoder among them — keep full width and are recorded as such.

Android has no runtime equivalent of `MLComputePlan`, and every Android accelerator is
half-precision hardware, so the catalogue carries the Core ML decision across. `acceleratesWell` is
true exactly for the models admitted at half-precision arithmetic, and `MavModelAcceleration` offers
those the GPU delegate — float16 by default, gated on the vendor's own `CompatibilityList`, with
NNAPI second and not attempted above API 34 where the platform deprecated it. Everything else runs
XNNPACK at full width, matching what those models do on iOS. Shipping the same bytes to both
platforms is not parity; computing the same arithmetic is.

The cost is a gate that has to know what it is measuring. Where Core ML kept full width the host
cross-platform comparison is like for like and is held at 5e-3; where Core ML runs half width the
host comparison comes from a float16 answer and a float32 interpreter, so it is an upper bound and
is bounded where the reference gate is. On device the two converge.

### 7. Two PPG front-ends, and why both stay

Every PPG head is a head over an embedding. Maverick's own encoder, PulseNet-Foundation, is the one
the hypertension heads were fitted against. Pulse-PPG (Xu et al., UbiComp 2025, MIT) is
third-party, open, and pre-trained on roughly 200 million seconds of uncurated wrist PPG from a
100-day field study — the regime Maverick operates in.

Both ship. Pulse-PPG is the default front-end because it generalises across the widest range of
wear conditions; PulseNet stays because `halite_ppg_score` reads *its* embedding space, and
swapping an encoder under a head is not a substitution a contract can make silently.

### 8. Standing is provenance, not quality

`ModelStanding` has two values: `FirstParty` for Maverick's own weights and `OpenLicensed` for
third-party weights under a permissive licence. It answers one question — does an upstream
attribution notice have to travel with the artefact — and nothing else. Today only `pulse_ppg` is
`OpenLicensed`.

How far an output may be *believed* is a separate axis and is not encoded here, because today the
answer is the same for every model in the zoo: provisional.

### 9. New error codes in `mav-model`

Five codes are added to the `Ml` range, which is a frozen-interface change and the reason this ADR
exists rather than a plan entry:

| Code | Meaning |
|---|---|
| 8004 | `ML_MODEL_TENSOR_INVALID` — a tensor does not match its registered contract |
| 8005 | `ML_MODEL_INFERENCE_INVALID` — a model returned values the contract cannot accept |
| 8006 | `ML_MODEL_NOT_ADMITTED` — the platform reported an unadmitted artefact hash |
| 8007 | `ML_MODEL_PREPROCESSING` — a front-end could not produce a tensor from its signal |
| 8008 | `ML_MODEL_REQUEST_UNKNOWN` — no inference is outstanding for that id |

They are additive: no existing code changes meaning, and no stored row is reinterpreted.

## Consequences

A zoo ships where one classifier did, and every model in it is provisional. Software behaviour is
fixture-covered, conversion parity is recorded, and nothing has been checked against labelled
ground truth. None is wired into `DailySnapshot`. Admitting a model into the snapshot remains a
separate decision per model under the rule in [testing.md](../testing.md), which is what stops a
registry of models from becoming a screen of unvalidated numbers. The count itself lives in
`artifacts/models/manifest.json` and is deliberately not restated here.

The bundle grows. The exact figures live in `artifacts/models/manifest.json` under `bundle_bytes`
so they cannot drift out of a document. iOS is the smaller of the two for one reason: Core ML
halves its weights by default and TensorFlow Lite does not.

Six *wrapper archives* did not convert, and `manifest.json` lists them under `not_shipped` with the
converter error that stopped each one. None of the six is a lost capability: in every case the
wrapper failed on data-dependent control flow and its neural cores were exported separately and do
ship — `whr_unet` as an encoder and a head, `cva_predictor` as an encoder and two probe branches,
and so on. What the wrapper was doing around those cores is reproduced in Rust, and `COMPOSITES` in
`pipeline.rs` records the pairing so a diagnostics surface can show the two together rather than
reading `not_shipped` as six missing features. The archives stay in `tools/ml/specs.py` with their
recorded errors so a later attempt starts from the failure.

Conversion needs the training checkpoints, which are held outside this repository. What is
reproducible without them is everything downstream of the contracts: the manifest, the generated
registries, and every test.

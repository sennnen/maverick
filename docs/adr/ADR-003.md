# ADR-003: Append-only raw storage

## Context

Health data from a strap is evidence, and it arrives exactly once; a decode or an analytic can be
rerun, but bytes a strap has trimmed from its own memory are gone. Both surveyed codebases
converged independently on the same storage shape: raw evidence kept immutable, derived data
treated as a computation over it. Both also demonstrated why: parsers were wrong and later fixed,
and the installs that had kept raw data could regenerate; anything decoded-then-discarded was stuck
with the old parser's mistakes.

## Decision

Storage has three tiers in one SQLite database. Tier one is append-only raw evidence,
content-addressed by sha256, inserted and never updated or deleted. Tier two is decoded frames,
each row stamped with the parser_version that produced it, regenerable from tier one. Tier three is
metrics and rollups, mutable via UPSERT with idempotency guards, recomputable at will. Migrations
are forward-only and numbered, with a schema-version pragma; a database newer than the code refuses
to open.

## Consequences

A parser bug costs a re-decode and an analytic bug costs a recompute; only tier one is
irreplaceable, and nothing in the system is permitted to revise it. The round-trip guarantee
(ADR and test: drop all derived tables, recompute, get identical values) stays checkable because
raw evidence is always present. The costs are disk (raw frames are kept, optionally in a bounded
ring) and the discipline that no code path may ever "fix" a raw row in place; corrections are new
data, mappings, or re-decodes, never edits to evidence.

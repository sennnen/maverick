# ADR-010: UniFFI for the bindings

## Context

A shared Rust core (ADR-001) still has to be called from Swift and Kotlin. Hand-written FFI means
maintaining a C ABI, two sets of foreign wrappers, and memory-safety rules at every crossing, all
by hand, twice; it is precisely the kind of repetitive, symmetry-demanding work where a swarm
introduces the platform divergence the shared core was meant to eliminate. The interface will also
change as milestones land, so the binding layer must be cheap to regenerate rather than expensive
to re-edit.

## Decision

The FFI boundary is generated by UniFFI from a single interface definition in mav-ffi. Both
platforms' bindings are generated from the same source, and mav-ffi is the only crate the native
shells link against. The exposed surface is deliberately coarse: snapshot queries, the
recent-errors query, the report bundle export, and the fixture-runner entry point the parity
harness uses.

## Consequences

The Swift and Kotlin views of the core cannot drift apart by hand-editing, because neither is
hand-edited; an interface change is made once and regenerated for both. What divergence remains
lives in the generated glue and the thin shells, and the fixture-hash parity harness exists to
catch exactly that. The costs are a build-time dependency on the UniFFI toolchain and acceptance
of its type-mapping limits, which push the design toward simple, serialisable boundary types; that
pressure aligns with the frozen mav-model types and is welcome rather than fought.

# ADR-022 — Clock correction is a mapping, applied per session

Status: accepted.

## Context

ADR-004 promised that a corrected clock is a stored mapping and a flag, never an edit to a raw
timestamp. `mav-model::time` duly grew `ClockMap`, `ClockSegment`, `to_wall`, and `anchored`, all
exported. Nothing called them.

What the timeline actually did was reinterpret the device timestamp as wall time when it looked
plausible, and otherwise place the sample at the instant the phone captured the frame. The second
branch is the damaging one: a burst of samples ten seconds apart in device time all land on one
capture instant, so every interval inside the burst becomes zero. Those intervals are the input to
variability analysis, and a strap whose RTC never latched real time — the normal state of a device
that has not synced — produces exactly that burst.

The oracle's correction is a single offset per session, trusted when small and snapped to a
five-minute grid when gross.

## Decision

`place_on_wall_with(map, sample, capture)` is the real placement. A plausible device time is trusted
directly. An implausible one is placed through the map, which shifts a whole segment by one offset
and therefore preserves every gap inside it. Only when the map covers nothing does the capture time
apply, and a corrected or fallen-back sample keeps `RejectReason::ImplausibleTimestamp` so the
inspector sees that no trustworthy clock produced it. Raw device timestamps are never rewritten.

`ConnectorHost` holds one `ClockMap` per session. The first implausible device time seen beside a
known host wall time anchors it, snapped to the five-minute grid; a device whose clock is fine
anchors nothing. One anchor suffices within a session because the device clock advances one-for-one
with wall time — that is what a `ClockSegment` asserts.

The grid snap is not cosmetic. It makes the same record, re-synced in a later session, correct to
the same wall time, so the store's natural key still recognises it as the sample it already holds.

## Consequences

Intervals survive a stale RTC, which is the whole point. Placement is honest about its provenance in
all three cases.

Cross-session persistence is **deferred**: `mav-store` has no clock tables, so a map is learned fresh
each session. That is acceptable while a session anchors from its own first implausible sample and
the grid snap makes independently-learned anchors agree. It stops being acceptable when a device is
observed across sessions whose captures disagree by more than a grid step, and at that point the map
becomes a stored table under a forward-only migration.

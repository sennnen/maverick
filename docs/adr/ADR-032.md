# ADR-032: Haptics are a connector-declared capability, not a device call

## Status

Proposed.

## Context

The workout lane needs the strap to buzz. The spec it is ported from
(`WORKOUT_HAPTIC_FEATURES.md`, from the Aura prototype) defines a small vocabulary and leans on it
throughout: a light tap at a distance marker or a halfway point, a hard buzz when an end condition is
met, a tap when a set is logged, a hard buzz when a rest timer ends, and a zone alert whose loop
count names the zone.

In the prototype every one of those was a direct call — `WhoopBleClient.buzz(3)`. That cannot come
across. Maverick has no `WhoopBleClient`; it has connectors, and [ADR-017](ADR-017.md) removed the
host's knowledge of what a device is. A hardcoded buzz would put a device family back in the app
binary, which is the failure that decision exists to prevent.

Nor is it safe to hand a connector a general "write to the strap whenever you like" affordance. A
connector is hostile by assumption. A driver that can vibrate a wrist at will is a nuisance vector at
best, and on a device worn during sleep it is worse than that.

There is also an honesty problem. Not every device can buzz. The Generic HR Monitor artifact the apps
ship cannot. WHOOP 4.0 and 5.0 do not necessarily expose the same patterns. A settings screen that
offers zone alerts on a strap that cannot deliver them is lying, and silently doing nothing when the
zone is crossed is the worst version of that lie.

## Decision

Haptics become a **declared capability with a semantic vocabulary**, following the shape
[ADR-031](ADR-031.md) established for device controls: the connector declares what it can do, the
host decides when it happens, and the connector translates.

- A connector may declare a `haptics/v1` block in its manifest, naming which signals of a **closed,
  host-owned vocabulary** it can render, and its bound on loop count. The vocabulary is
  `milestone`, `goal_complete`, `set_logged`, `rest_complete`, and `zone_alert(1..=5)`. A connector
  cannot extend it, because a signal the host cannot name is a signal the host cannot decide to send.
- The app requests a *signal*, never a byte pattern. The core delivers `EventBody::HapticRequest
  { signal }`, and the connector emits its own already-declared characteristic `Write` in response.
  Translation from meaning to opcode is connector knowledge and stays there.
- A connector may emit a haptic write **only while a host-initiated request is outstanding**, bounded
  by the same deadline token every other transport action carries. There is no unprompted buzz. A
  write to a haptic characteristic outside that window is a protocol violation and is journalled as
  one.
- Requests are rate-limited by the host, per session, and dropped with an error code rather than
  queued when the limit is exceeded. A dropped buzz is logged like any other dropped frame
  (`CLAUDE.md`: never drop silently); it is never retried, because a late buzz is a wrong buzz.
- Declaration is validated at inspection time and appears in the approval report beside capabilities
  and controls, so a user approving a connector has already seen that it can vibrate the device.
- Availability is negotiated, not assumed. `host-snapshot` gains a `haptics/v1` block listing the
  signals the *connected* connector declared. Any feature built on a signal renders through the
  existing unavailable-analytic component when that signal is absent, naming the reason.

Zone alerts and milestone cadences remain **user preferences stored by the app**, not connector
state. What the wearer wants to be told is not a property of the strap, and it must survive changing
straps.

## Consequences

- The workout lane can be built now against a stable vocabulary, and its haptic-dependent settings
  are honestly unavailable until a connector declares support. On the Generic HR Monitor they stay
  unavailable permanently, which is correct rather than a gap.
- Adding buzz support to a device is a connector release, not a Maverick release — the same property
  ADR-031 bought for controls.
- The manifest gains a section and a validation surface: signal-name set, loop bound, and aggregate
  limits, enforced before instantiation. An artifact without the section is unchanged, so every
  signed artifact stays valid and the ABI minor does not move.
- `host-snapshot`'s canonical fixture is re-blessed once. The block is empty for every existing
  connector, so no other fixture changes.
- The vocabulary being closed means a device with a genuinely novel haptic idea cannot express it
  without an ADR amending this list. That is deliberate. The alternative — connector-named signals —
  puts the host in the position of forwarding meaning it cannot reason about, and rate-limiting
  something it cannot categorise.
- This ADR specifies the contract; it does not implement it. Like ADR-031, it is proposed ahead of
  the lane that needs it, so that the app-side work can be built against a decided shape rather than
  an assumed one.
